# Atelier 1 : Ingestion dynamique multi-sources avec validation

## Contexte : Optimisation d'une chaîne d'approvisionnement en énergie renouvelable

Une **usine de production traditionnelle** décide de migrer vers un modèle hybride solaire-éolien. Les données énergétiques proviennent de multiples capteurs et systèmes (consommation actuelle, production solaire, production éolienne, stockage batteries).

### 1. État des lieux

- **3 sources de données** quotidiennes :
  - `besoins_energetiques.csv` (consommation horaire de l'usine)
  - `production_solaire.csv` (rendement des panneaux par zone)
  - `production_eolienne.csv` (données des turbines)
- **Dépôt non structuré** : fichiers déposés manuellement dans un dossier
- **Absence de validation** : impossible de savoir si toutes les sources sont arrivées
- **Processus manuel** : un technicien vérifie et importe les fichiers dans Excel

### 2. Problématique

Comment automatiser l'ingestion de données énergétiques hétérogènes pour analyser les besoins actuels et identifier les sources renouvelables disponibles, sans intervention manuelle et avec validation de la complétude ?

Contraintes :

- ✅ Détecter dynamiquement quels fichiers sont présents
- ✅ Ignorer les fichiers non-CSV (logs techniques, images...)
- ✅ Créer une table Bronze par source énergétique
- ✅ Tracer les fichiers ingérés pour l'audit

### 3. Solution : Pipeline d'ingestion intelligent

Pipeline qui scanne, filtre, copie et trace automatiquement toutes les sources énergétiques vers Bronze.

# Astuce: Importer et exporter et un pipeline en JSON

## Objectif

- Comprendre qu'un pipeline Fabric est un **fichier JSON** (`pipeline-content.json`).
- Le **sauvegarder / versionner / dupliquer** hors de l'interface.
- Le **réimporter** dans le même workspace ou un autre, et savoir ce qu'il faut reconnecter.

## A. Exporter le pipeline

1. Ouvrir `PL_Ingestion_Energie_Bronze` dans l'éditeur de pipeline.

2. Onglet **Home** de la barre d'outils : cliquer sur l'icône **Export** (flèche vers la droite, entre *Save as* et *Import*).

3. Le navigateur télécharge un **fichier `.zip`** nommé d'après le pipeline
   
    (`PL_Ingestion_Energie_Bronze.zip`) sur votre **PC** 
   
   (dossier *Téléchargements* par défaut).

4. Le déplacer dans un dossier de travail, ex. `Module 3 Les piplines ms fabric/exports/`, pour le retrouver facilement à l'import.

5. Variante lecture seule : afficher le code JSON du pipeline (onglet **View**, option du type *JSON code*) **[à vérifier]**.

À noter : contenu exact du zip (fichiers présents, dont `pipeline-content.json`).

## B. Lire le JSON

Ouvrir `pipeline-content.json` dans un éditeur. Repérer :

- **`properties.activities`** : une entrée par activité (`ScanLanding`, `BouclerFichiers`, puis à l'intérieur `EstCSV`, `CopierVersBronze`, `TracerFichier`, `RecupererTracage`).
- **`type`** : `GetMetadata`, `ForEach`, `IfCondition`, `Copy`, `AppendVariable`, `SetVariable`.
- **`dependsOn`** : l'ordre d'exécution (flèches vertes/rouges du canvas = conditions `Succeeded`/`Failed`).
- **Expressions** : objets `{"value": "@item().name", "type": "Expression"}`.
- **`properties.variables`** : `FichiersTraites`, `FichierActuel`, `NombreFichiers`, `FichiersTemp`.
- **Références au lakehouse** : `workspaceId`, `artifactId`, `rootFolder` (`Files` en source, `Tables` en destination). **Ce sont ces identifiants qui changent d'un workspace à l'autre.**

## C. Créer un pipeline de test et y importer le zip exporté depuis le PC

L'import se fait **depuis l'éditeur d'un pipeline**, avec l'icône **Import** de l'onglet **Home** (flèche vers la barre, à droite d'*Export*). On l'applique à un **pipeline de test vide**, afin de ne pas toucher l'original.

1. Dans `WS_Energie_Renouvelable` : **+ New item → Data pipeline**, nom `PL_Test_Import` (pipeline vide, canvas sans activité).
2. Dans son éditeur, onglet **Home** → **Import**.
3. Une boîte **File Upload** (explorateur de fichiers de votre PC) s'ouvre : naviguer jusqu'au dossier de l'étape A et sélectionner **`PL_Ingestion_Energie_Bronze.zip`** (le zip déjà exporté).
4. L'écran **modèle (template)** s'affiche : aperçu du pipeline (Get Metadata `ScanLanding` → ForEach `BouclerFichiers` → `EstCSV`), description (« Ingestion des CSV landing vers les tables Bronze ») et section **Inputs**.
5. Dans **Inputs**, le champ **Lakehouse *** (*For ScanLanding (GetMetadata), EstCSV (IfCondition)*) est obligatoire : il propose *No results found* tant qu'aucune connexion n'est choisie. Cliquer **Browse all** (ou le bouton d'actualisation) puis sélectionner **`LH_Energie_Bronze`**, le lakehouse qui contient les données.
6. Valider l'import (bouton de confirmation de l'écran, libellé **[à vérifier]**).
7. Contrôler le canvas : 2 activités à la racine, `EstCSV` dans le ForEach avec ses 3 activités internes ; onglet Home → **Validate** sans erreur ; variables présentes (`FichiersTraites`, `FichiersTemp`, …).

**Exercice de modification (facultatif)** : avant l'étape 3, ouvrir le zip, éditer `pipeline-content.json` dans une *copie* (ex. `"retry": 0` → `"retry": 2` sur `CopierVersBronze`), recompresser avec la même arborescence, puis importer ; vérifier ensuite Retry = 2 dans l'onglet Settings de l'activité.

## D. Contrôles

- Comparer visuellement le pipeline importé et l'original (mêmes activités, mêmes dépendances, mêmes expressions).
- Vérifier la modification de l'étape C (ex. **Retry = 2** dans l'onglet Settings de `CopierVersBronze`).
- **Ne pas lancer** le pipeline importé sans nettoyage : la destination est en **Append**, un run ajouterait 30 lignes de plus par table (doublons). Si exécution voulue : vider les tables Bronze avant ou accepter les doublons pour l'illustration.

## E. Cas d'usage à retenir

- **Sauvegarde / versionnement Git** : le JSON est lisible et comparable (diff).
- **Duplication / environnements** (Dev → Test → Prod) : réimporter puis reconnecter les sources (les `workspaceId`/`artifactId` pointent vers un autre workspace). Les **deployment pipelines** de Fabric automatisent cela.
- **Génération par script/API** : un pipeline peut être créé en envoyant ce JSON (encodé en Base64) à l'API REST Fabric (`definition.parts`) : c'est la méthode utilisée pour l'automatisation.

# Astuce : planifier le pipeline et le surveiller dans Monitor

## Objectif

- Exécuter `PL_Ingestion_Energie_Bronze` **automatiquement** à intervalle régulier.
- Retrouver et analyser ces exécutions dans le hub **Monitor** (menu de gauche).

## Avant de commencer : attention à l'Append

La destination du Copy data est en **Append** : chaque exécution ajoute 30 lignes par table. Pour l'exercice :

- planifier une période **courte** (quelques exécutions) ;
- **désactiver ou supprimer** la planification à la fin ;
- compter ensuite les lignes (30 × nombre de runs + 30) : c'est le point de départ de la discussion sur l'**idempotence** (Overwrite, ou logique incrémentale).

## 1. Créer la planification

1. Ouvrir `PL_Ingestion_Energie_Bronze`.
2. Onglet **Home** → **Schedule**, puis **Add Schedule**.
3. Choisir le type : **Fixed schedule** (fréquence minute / heure / jour / semaine / mois). *L'option **Interval-based schedule** existe en préversion : non utilisée ici.*
4. Renseigner :
   - **Repeat / fréquence** : toutes les **5 minutes** (pour le test) ;
   - **Start date and time** : dans 2 à 3 minutes ;
   - **End date and time** : environ 15 minutes après le début ;
   - **Time zone** : fuseau de Paris ;
   - bascule d'activation : **activée**. **[libellés exacts à constater]**
5. **Save**.

Règles de la documentation :

- une **date de début et une date de fin sont obligatoires** : il n'y a pas de planification sans fin (pour une exécution permanente, mettre une date très lointaine, ex. `01/01/2099 12:00 AM`) ;
- jusqu'à **20 planifications** par pipeline, chacune avec sa fréquence et ses dates ;
- les **paramètres** de pipeline peuvent recevoir des valeurs à chaque exécution planifiée (noms identiques à ceux du pipeline) ; non utilisé ici ;
- **Failure notifications** (même panneau) : notification e-mail à des utilisateurs/groupes **en cas d'échec d'un run planifié** (jamais pour un run manuel).

## 2. Suivre les exécutions dans le pipeline

- Onglet **Home** (ou **Run**) → **View run history** : liste des exécutions de ce pipeline.
- Attendre l'heure de début : une nouvelle ligne apparaît à chaque intervalle.

## 3. Suivre les exécutions dans Monitor

1. Menu de gauche → **Monitor** (le hub de surveillance de Fabric ; vous ne voyez que les éléments auxquels vous avez accès).
2. Page **Job runs**.
3. Filtrer : **plage de temps** (dernière heure, 6 h, 24 h, N jours), **Item type** = Data pipeline, **Status** (In progress, Succeeded, Failed, Canceled), **Workspace**, ou recherche par nom (`PL_Ingestion_Energie_Bronze`).
4. Colonnes documentées : **Item name**, **Last run status**, **Average duration**, **Last run details**. Colonnes supplémentaires via **Manage view → Column Options**. **[à constater : colonne indiquant planifié / manuel et ses libellés]**
5. Cliquer sur une exécution : le **panneau de détails** affiche l'historique ; pour un pipeline : flux d'exécution, tableau des activités et diagramme de Gantt. Icônes **Open detail page** (page complète) et **Open item** (retour à l'éditeur) ; bouton **Refresh**.
6. En cas d'échec : bouton **Investigate** (agent Operations, préversion — voir remarque plus bas).

## 4. Gérer la planification

- **Home → Schedule** : modifier, ou activer/désactiver avec la bascule.
- Suppression : icône **Edit** (crayon) → **Delete schedule** en bas du panneau.
- Les schedules en préversion de type *Interval-based* ne sont ni éditables ni désactivables : suppression/recréation.

## 5. Vérifier l'effet sur les tables (Append)

Après les exécutions, compter les lignes de chaque table du lakehouse : le total augmente de 30 à chaque run. Conclusion : un pipeline planifié doit être **idempotent** (Overwrite pour un chargement complet, ou filtrage des fichiers déjà traités).

# Section : remplacer Copy data par Copy job

## Objectif

Réaliser le **même chargement Bronze** avec Copy data puis avec Copy job, et comparer. Le pipeline d'origine n'est **pas modifié** : on travaille sur une copie, et les tables de la variante sont suffixées `_cj`.

## Principe

- **Copy data** : activité *paramétrable* d'un pipeline ; une seule activité sert aux 3 fichiers grâce à `@item().name`.
- **Copy job** : *item autonome* du workspace ; il faut **d'abord le créer et le configurer** (source, destination, mode de copie), puis le sélectionner dans une activité **Copy job**.
- **Limite constatée** : l'activité Copy job (onglets General et Settings) ne propose **ni paramètre ni champ de nom de fichier** ; elle désigne **un Copy job précis**. Le JSON stocké ne contient que `copyJobId`, `workspaceId` et `operationType: "RunCopyJob"`. D'où : **un Copy job par fichier**, aiguillés par une activité **Switch** sur `@item().name`.

## Pièges

- Le Copy job doit **exister et être configuré** avant d'être sélectionné dans le pipeline.
- **Append + plusieurs runs = doublons** ; ici **Overwrite** est utilisé.
- Schedule du pipeline **et** schedule du Copy job actifs : doubles exécutions ; garder un seul propriétaire de l'orchestration (le pipeline).
- Aucune sortie documentée du Copy job (ex. lignes copiées) utilisable en expression : `TracerFichier` repose sur `@item().name`.

## Partie 1 : créer et configurer 3 Copy jobs

## Comparaison à remplir

| Critère                           | Copy data                  | Copy job                       |
| --------------------------------- | -------------------------- | ------------------------------ |
| Éléments à créer pour 3 fichiers  | 1 activité                 | 3 items + Switch + 3 activités |

| Relance sans doublons             | selon Append / Overwrite   | Overwrite configuré            |
| Mode incrémental / CDC natif      | non (à concevoir)          | oui (Full, incrémental, CDC)   |

À discuter ensuite (documenté par Microsoft) :

- Copy data convient à l'ingestion **pilotée par métadonnées** (liste de fichiers ou de tables dynamique, `ForEach`, expressions).
- Copy job convient à une copie **simple et maintenable** (Bronze, bulk, incrémental, CDC) avec moins de plomberie.
- Capacité : Full ≈ 1,5 CU-h, incrémental ≈ 3 CU-h (par ressource/heure d'exécution) ; vérifier avec l'app **Capacity Metrics**. Pas de « toujours moins cher ou plus rapide ».

## Variante hors boucle

Un **seul** Copy job à trois correspondances, invoqué **une seule fois** après `ScanLanding`, sans ForEach ni If. Plus simple et plus représentatif du produit, mais la boucle et la traçabilité perdent leur utilité.

> À éviter : un Copy job unique **dans** le ForEach : il recopierait les 3 fichiers à chaque itération.

# Section : ingestion depuis une API REST (Copy data)

## Objectif

Remplacer la lecture des fichiers CSV (`GetMetadata` → `ForEach` → `If Condition` → `Copy data`) par la lecture de trois **endpoints HTTP** avec une seule activité **Copy data** à source REST, pilotée par un paramètre.

## Prérequis

- Les tables Bronze existent déjà (`besoins_energetiques`, `production_solaire`, `production_eolienne`) : toutes les colonnes y sont en `string`.
- Le service d'API (Azure Function, anonyme, GET) est fourni : l'apprenant n'a que les points de terminaison.

## Points d'attention

- **Ne pas relancer sans vider** : doublons en Append.
- **Pagination** : non utilisée ici (30 lignes par endpoint) ; une API réelle volumineuse demande des *pagination rules* dans la source.
- **Authentification** : l'API pédagogique est anonyme ; en production, préférer une authentification (Service principal, Basic, etc.) et ne jamais mettre de secret dans le JSON.
- **Typage** : volontairement reporté en Silver.

| Endpoint                                                                      | Table Bronze           | Lignes |
| ----------------------------------------------------------------------------- | ---------------------- | ------ |
| `https://func-energie-api-1ae13f08.azurewebsites.net/api/besoins`             | `besoins_energetiques` | 30     |
| `https://func-energie-api-1ae13f08.azurewebsites.net/api/production-solaire`  | `production_solaire`   | 30     |
| `https://func-energie-api-1ae13f08.azurewebsites.net/api/production-eolienne` | `production_eolienne`  | 30     |

Un endpoint `/api/health` permet de vérifier que le service répond.

## Partie 1 – Découvrir les données

1. Ouvrir chaque URL dans le navigateur.
2. Constater : réponse JSON = tableau d'objets, une clé par colonne (mêmes noms que les CSV), nombres en JSON numérique, dates en texte ISO.

## Partie 2 – Créer la connexion

1. Workspace → **Settings (engrenage)** → **Manage connections and gateways** → **New**.
2. Choisir **Cloud**, puis renseigner :

| Champ                 | Valeur                                                 |
| --------------------- | ------------------------------------------------------ |
| Connection name       | `Rest`                                                 |
| Connection type       | **Web v2**                                             |
| Base Url              | `https://func-energie-api-1ae13f08.azurewebsites.net/` |
| Token Audience Uri    | vide                                                   |
| Authentication method | **Anonymous**                                          |
| Privacy level         | Organizational                                         |

3. **Create**. Ouvrir ensuite les paramètres de la connexion et noter le **Connection ID** (GUID).

> Le connecteur Web v2 est celui utilisé par la source REST de Copy data.

## Partie 3 – Importer le pipeline

1. Créer un pipeline de test vide (ex. `PL_Test_REST`).
2. **Import/Export** → **Import pipeline** → fichier `PL_Ingestion_Energie_Bronze_REST.json` (dossier `data etude de cas 1`).
3. Si le fichier contient encore `<REST_CONNECTION_ID>`, le remplacer par le GUID de la connexion avant l'import.
4. Ouvrir `BouclerEndpoints` → `CopierRestVersBronze` → onglet **Source** :
   - **Connection** : si une erreur « Failed to load the connection » apparaît, sélectionner **Rest** dans la liste.
   - **Test connection**, puis **Preview data** pour vérifier la lecture.
5. Onglet **Destination** : vérifier que le Lakehouse est `LH_Energie_Bronze` ; le reselectionner si l'import ne le reconnaît pas dans votre workspace. [à constater selon le workspace]

## Partie 4 – Comprendre le pipeline

| Élément                                  | Rôle                                                                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Paramètre `Endpoints` (Array)            | Liste de 3 objets `{ relativeUrl, table, mappings }` : un par source                                                              |
| `BouclerEndpoints` (ForEach, séquentiel) | Parcourt la liste ; séquentiel car les variables ne sont pas thread-safe                                                          |
| `CopierRestVersBronze` (Copy data)       | Source REST : **Relative URL** = `@item().relativeUrl` ; destination : table = `@item().table` ; **Mapping** = `@item().mappings` |
| `TracerFichier` / `RecupererTracage`     | Gardent la trace des tables alimentées (variables `FichiersTemp`, `FichiersTraites`)                                              |

Points clés :

- **Une seule** Copy data pour trois sources : ajouter une source = ajouter un objet dans `Endpoints`.
- **Mapping explicite par table** : une API renvoie des objets JSON, le mapping associe `$['Colonne']` → colonne de la table.
- **Types** : source `Double` pour les nombres, mais destination `String`, car les tables Bronze sont entièrement en `string`. Le typage (dates, décimaux) se fait en **Silver**.

## Partie 5 – Exécuter et vérifier

1. **Vider les tables Bronze avant** (le mode est **Append** : relancer sans vider donne 60 lignes au lieu de 30).
2. **Run** du pipeline.
3. Dans la vue d'exécution : 3 itérations de `CopierRestVersBronze` dans le ForEach, toutes **Succeeded**.
4. Dans le Lakehouse : 30 lignes par table, colonnes en `string`.

## Comparaison des deux approches

|                        | Fichiers CSV                               | API REST                       |
| ---------------------- | ------------------------------------------ | ------------------------------ |
| Source                 | Fichiers du Lakehouse (landing)            | Endpoints HTTP                 |
| Découverte des sources | `GetMetadata` + `ForEach` + `If Condition` | Liste `Endpoints` (paramètre)  |
| Mapping                | Automatique (CSV tabulaire)                | Explicite (JSON)               |
| Authentification       | Aucune (Lakehouse)                         | Connexion Web v2               |
| Nouvelle source        | Déposer un fichier                         | Ajouter un objet à `Endpoints` |

## Insights métier

### Insight 1 : Équilibre énergétique préliminaire

**Calculez la capacité renouvelable théorique** :

```sql
-- Production solaire moyenne
SELECT AVG(Production_kWh) as Prod_Solaire_Moyenne
FROM production_solaire
-- Résultat attendu : ~350 kWh/jour (25 panneaux × 14 kWh)

-- Production éolienne moyenne
SELECT AVG(Production_kWh) as Prod_Eolienne_Moyenne
FROM production_eolienne
-- Résultat attendu : ~1200 kWh/jour (5 turbines × 240 kWh)

-- Besoin énergétique quotidien
SELECT SUM(Consommation_kWh) / 7 as Conso_Quotidienne
FROM besoins_energetiques
-- Résultat attendu : ~1800 kWh/jour
```

**Analyse de couverture** :

```
Production renouvelable : 350 (solaire) + 1200 (éolien) = 1550 kWh/jour
Besoin énergétique : 1800 kWh/jour
Taux de couverture : (1550 / 1800) × 100 = 86%
Déficit : 1800 - 1550 = 250 kWh/jour (14%)
```

**Interprétation** :

- **86% d'autonomie énergétique** avec les sources renouvelables
- **14% de déficit** à combler (réseau traditionnel ou batteries)
- **Objectif atteint** : Réduction significative de la dépendance au réseau

💡 **Recommandations métier** :

1. Ajouter **5 panneaux solaires** supplémentaires (+70 kWh/j) pour atteindre 90% d'autonomie
2. Installer un **système de batteries** de 250 kWh pour stocker les surplus et couvrir les pics
3. Implémenter un **système de délestage intelligent** pour reporter certaines charges non prioritaires
