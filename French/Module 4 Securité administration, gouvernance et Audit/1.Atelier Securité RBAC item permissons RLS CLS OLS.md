# Couche 1 — RBAC Workspace

## Étape 1 — Attribuer le rôle Workspace Viewer au compte participant

**Objectif** : Créer un environnement Fabric minimal, attribuer le rôle **Viewer** au compte participant et vérifier concrètement les accès accordés par ce rôle sur un Lakehouse et son point de terminaison SQL.

**Pourquoi** :  
Le rôle Workspace Viewer est le seul rôle qui n’autorise aucune modification ni exécution dangereuse.

Il constitue le plafond de sécurité pour tous les utilisateurs finaux.

| Rôle            | Capacités principales                                                               | Gestion des accès et du partage                                                                          | Usage type                                       |
| --------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Admin**       | Dispose du contrôle complet sur le workspace et son contenu.                        | Peut ajouter ou retirer tous les utilisateurs                                                            | Propriétaire ou administrateur de la plateforme. |
| **Member**      | Peut créer, modifier, exécuter et supprimer les objets et les données du workspace. | Peut ajouter des **Members**, des **Contributors** et des **Viewers** outre que les droit de contributor | Responsable d’équipe ou gestionnaire de contenu  |
| **Contributor** | Peut, comme un **Member**, créer, modifier, exécuter et supprimer les objets        | Ne peut pas gérer les rôles du workspace ni ajouter des utilisateurs.                                    | Développeur ou concepteur                        |
| **Viewer**      | Peut consulter le contenu du workspace sans le modifier. .                          | Ne peut pas gérer les accès.                                                                             | Lecteur, analyste métier                         |

> 

**Actions formateur (compte dev – Workspace Admin)** :

1. Connectez-vous à Microsoft Fabric avec le compte **dev**.

2. Créez un workspace nommé **FinCorp_Initial** et vérifiez que le compte **dev** possède le rôle **Admin** sur ce workspace.

3. Dans le workspace **FinCorp_Initial**, sélectionnez **+ New item**, puis créez un **Lakehouse** nommé **LH_FinCorp**.

4. Ouvrez **LH_FinCorp**, puis chargez le fichier `Data/Sales_FinCorp.csv` fourni avec l’atelier dans la section **Files** du Lakehouse :
   
   - sélectionnez **Files** puis **Upload** ;
   - choisissez **Upload files** ;
   - sélectionnez le fichier `Sales_FinCorp.csv` ;
   - vérifiez que le fichier apparaît sous **Files**.

5. Revenez dans le workspace **FinCorp_Initial** et créez un notebook nommé **NB_Load_SalesFinCorp**.

6. Attachez **LH_FinCorp** comme Lakehouse par défaut du notebook.

7. Conservez une seule cellule PySpark dans le notebook, puis saisissez et exécutez le code suivant :

```python

df.write.mode("overwrite").format("delta").saveAsTable("sales_fincorp")
display(spark.table("sales_fincorp"))
```

8. Revenez dans **LH_FinCorp**, actualisez la section **Tables** et vérifiez que la table **sales_fincorp** est visible.

9. Ouvrez le workspace **FinCorp_Initial**, puis cliquez sur **Manage access** en haut à droite.

10. Cliquez sur **+ Add people or groups**.

11. Dans la zone de recherche, saisissez le nom ou l’adresse du compte **participant**, puis sélectionnez-le.

12. Dans la liste des rôles, choisissez **Viewer**.

13. Cliquez sur **Add**.

**Ce que le formateur doit vérifier** :

- Le workspace **FinCorp_Initial** contient le Lakehouse **LH_FinCorp**, son point de terminaison SQL et le notebook **NB_Load_SalesFinCorp**.

- Le fichier `Sales_FinCorp.csv` apparaît dans **Files** et la table **sales_fincorp** apparaît dans **Tables**.

- Le compte **participant** possède uniquement le rôle **Viewer** dans le workspace.

3. Ouvrez le Lakehouse **LH_FinCorp**.

4. Observez les sections **Files** et **Tables**, puis essayez d’ouvrir le fichier `Sales_FinCorp.csv` et de prévisualiser la table **sales_fincorp**.

- Dans le **SQL analytics endpoint** associé au Lakehouse, le participant peut visualiser les tables, consulter les données et exécuter des requêtes SQL en lecture, notamment sur **dbo.sales_fincorp**.

- Dans le notebook **NB_Load_SalesFinCorp**, le participant peut visualiser les cellules ainsi que les résultats des exécutions précédentes, mais il ne peut pas exécuter les cellules ni lancer une nouvelle session.

- Il ne peut pas créer, modifier, supprimer ou administrer les objets du workspace. Les commandes telles que **New**, **Edit**, **Delete** et **Manage permissions** sont absentes ou désactivées.

La permission **ReadAll** autorise la lecture des données du Lakehouse avec Apache Spark et les API OneLake.

 Elle permet notamment au participant de parcourir les fichiers et les tables depuis l’explorateur du Lakehouse.

 Elle n’accorde pas de droit d’écriture.

5. Vérifiez que **ReadAll** apparaît désormais avec **Read** et **ViewOutput**.

2. Ouvrez **LH_FinCorp**.

3. Développez **Files**, ouvrez `Sales_FinCorp.csv`, puis essayez d’en afficher un aperçu.

4. Développez **Tables**, ouvrez **sales_fincorp**, puis essayez d’en afficher un aperçu.

## Étape 5 — Comparer Write, Execute et Reshare sur le notebook

**Objectif** : Distinguer les permissions de modification, d’exécution et de partage, puis restaurer le notebook dans son état initial.

**Pourquoi** :
Les permissions du notebook sont indépendantes et peuvent être combinées. **Read + Write** correspond au mode **Edit**, **Read + Execute** au mode **Run only**, et **Read + Write + Execute** au mode **Develop**. La permission **Reshare** concerne uniquement le partage du notebook.

**Actions formateur** :

1. Dans **Manage permissions** de **NB_Load_SalesFinCorp**, ajoutez **Write** au compte **participant** avec l’option **Add write**.

2. Modifiez temporairement le contenu de la cellule et vérifiez que la modification peut être enregistrée.

3. Essayez d’exécuter la cellule.

**Ce que vous devez voir — à confirmer par le test** :

- Le participant peut modifier et enregistrer le notebook.

- Il ne peut pas exécuter la cellule tant que **Execute** n’est pas ajouté.

### Test B — Combiner Write et Execute

**Actions formateur** :

1. Sans retirer **Write**, ajoutez **Execute** au participant avec **Add execute**.

2. Vérifiez que ses permissions sont maintenant **Read**, **Write** et **Execute**.

**Actions participant** :

1. Ouvrez le notebook en mode **Develop**.

2. Vérifiez que vous pouvez modifier la cellule, l’exécuter et enregistrer le notebook.

**Ce que vous devez voir — à confirmer par le test** :

- La combinaison **Read + Write + Execute** donne accès au cycle complet de développement du notebook.

- Le participant reste **Viewer** au niveau du workspace, mais dispose de droits supplémentaires uniquement sur **NB_Load_SalesFinCorp**.

### Test C — Ajouter Reshare

**Actions formateur** :

1. Ajoutez **Reshare** au participant avec l’option **Add reshare**.

**Actions participant** :

1. Vérifiez que l’action de partage du notebook est disponible.

2. Ouvrez la fenêtre de partage sans accorder réellement l’accès à un autre utilisateur.

**Ce que vous devez voir — à confirmer par le test** :

- **Reshare** permet de partager le notebook ; cette permission n’ajoute ni capacité d’édition ni capacité d’exécution.

### Nettoyage — Revenir au baseline Viewer

**Actions formateur** :

1. Dans **Manage permissions**, retirez successivement **Reshare**, **Execute** et **Write** du compte **participant**.

2. Vérifiez qu’il ne reste que **Read** sur **NB_Load_SalesFinCorp**.

3. Vérifiez également que **LH_FinCorp** affiche uniquement **Read** et **ViewOutput** pour le participant.

- Le Lakehouse est revenu à **Read, ViewOutput** et le notebook à **Read**.

- Le participant peut consulter le notebook et ses résultats enregistrés, mais ne peut plus le modifier, l’exécuter ou le partager.

## Étape 2 — Créer la fonction de prédicat et la politique RLS

**Objectif** : Autoriser le compte **participant** à lire uniquement les lignes Europe tout en conservant l’accès complet du compte **dev**.

**Actions formateur (compte dev)** :

1. Ouvrez une nouvelle requête dans le **SQL analytics endpoint** de **LH_FinCorp**.

2. Créez le schéma destiné aux objets de sécurité :

```sql
CREATE SCHEMA Security;
GO
```

> Si le schéma **Security** existe déjà à la suite d’un essai précédent, ne réexécutez pas cette commande.

3. Créez la fonction table de prédicat :

```sql
CREATE FUNCTION Security.fn_sales_region
(
    @Region varchar(8000)
)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
(
    SELECT 1 AS access_granted
    WHERE
        (
            USER_NAME() = 'participant@contactemeraudeit.onmicrosoft.com'
            AND @Region = 'Europe'
        )
        OR USER_NAME() = 'dev@contactemeraudeit.onmicrosoft.com'
);
GO
```

4. Associez cette fonction à la colonne **Region** de la table :

```sql
CREATE SECURITY POLICY Security.SalesFinCorpRegionPolicy
ADD FILTER PREDICATE Security.fn_sales_region(Region)
ON dbo.sales_fincorp
WITH (STATE = ON);
GO
```

5. Vérifiez que la politique est active :

```sql
SELECT
    name,
    is_enabled
FROM sys.security_policies
WHERE name = 'SalesFinCorpRegionPolicy';
```

**Ce que vous devez voir** :

- La politique **SalesFinCorpRegionPolicy** apparaît avec `is_enabled = 1`.

- La fonction autorise toutes les régions pour **dev**, uniquement Europe pour **participant**, et aucune ligne pour les autres identités.

6. Testez la désactivation de la politique sans la supprimer :

```sql
ALTER SECURITY POLICY Security.SalesFinCorpRegionPolicy
WITH (STATE = OFF);
GO
```

7. Vérifiez son nouvel état :

```sql
SELECT
    name,
    is_enabled
FROM sys.security_policies
WHERE name = 'SalesFinCorpRegionPolicy';
```

**Ce que vous devez voir** : la politique existe toujours, mais `is_enabled = 0`. Le filtre RLS n'est plus appliqué tant qu'elle reste désactivée ; les autres permissions SQL continuent de s'appliquer.

> 💡 **Désactiver ou supprimer ?** `STATE = OFF` conserve la politique et sa fonction afin de pouvoir les réutiliser rapidement. `DROP SECURITY POLICY` supprime l'objet et sert au nettoyage définitif présenté à l'étape 6.

8. Réactivez la politique avant de poursuivre les tests RLS :

```sql
ALTER SECURITY POLICY Security.SalesFinCorpRegionPolicy
WITH (STATE = ON);
GO
```

9. Relancez la requête sur `sys.security_policies` et vérifiez que `is_enabled = 1`.

- Le participant voit de nouveau les régions **Afrique**, **Asie** et **Europe**, soit les **300 transactions**.

- Le montant total redevient **7 099 330,37**.

- Le rapport n’est plus filtré par la RLS SQL.

- L’environnement est prêt pour tester la CLS indépendamment de la RLS dans la couche 4.

# Couche 4 — Sécurité des colonnes et des objets dans le point de terminaison SQL (CLS/OLS)

La politique RLS de la couche 3 a été supprimée. Cette couche isole donc l’effet de la **sécurité au niveau des colonnes (CLS)** dans le même **SQL analytics endpoint** :

- le participant peut de nouveau lire toutes les lignes de **dbo.sales_fincorp** ;
- les permissions SQL vont autoriser les colonnes utiles et bloquer **Salary** ;
- le compte **dev** conserve l’accès complet aux lignes et aux colonnes.

La sécurité au niveau objet peut être appliquée avec deux granularités complémentaires :

- la **Column-Level Security (CLS)** protège une ou plusieurs colonnes précises d’une table ;
- l’**Object-Level Security (OLS)** appliquée à la table protège l’objet entier et empêche toute lecture de ses colonnes.

La CLS peut ainsi être considérée comme une forme ciblée de sécurité objet au niveau colonne, tandis que l’OLS de table agit sur l’ensemble de la table. Cette couche commence par la CLS, puis se termine par un blocage de la table entière afin d’introduire l’étude de cas suivante.

---

## Étape 1 — Vérifier l’accès initial à la colonne Salary

**Objectif** : Confirmer qu’avant l’application de la CLS, les deux comptes peuvent lire la colonne **Salary**.

**Actions formateur (compte dev)** :

1. Choisissez l’éditeur SQL de Fabric ou SSMS, puis connectez-vous au point de terminaison de **LH_FinCorp** avec le compte **dev**.

2. Exécutez :

```sql
SELECT TOP 10
    USER_NAME() AS CurrentUser,
    SalesRep,
    Salary
FROM dbo.sales_fincorp;
```

**Actions participant** :

1. Dans l’outil de votre choix, connectez-vous au même point de terminaison avec le compte **participant**.

2. Exécutez la même requête.

**Ce que vous devez voir** :

- La requête réussit pour les deux comptes et affiche **SalesRep** et **Salary**.

- `CurrentUser` correspond au compte utilisé dans chaque session.

- Ce résultat constitue l’état de référence avant l’application de la CLS.

---

## Étape 2 — Appliquer la CLS au compte participant

**Objectif** : Autoriser les colonnes nécessaires aux analyses SQL et refuser explicitement la colonne **Salary** au participant.

**Actions formateur (compte dev)** :

1. Avec le compte **dev**, ouvrez une nouvelle requête dans l’éditeur SQL de Fabric ou dans SSMS.

2. Accordez au participant la lecture des colonnes autorisées :

```sql
GRANT SELECT ON dbo.sales_fincorp
(
    TransactionID,
    Region,
    SalesRep,
    Amount,
    ClientName,
    Date
)
TO [participant@contactemeraudeit.onmicrosoft.com];
GO
```

3. Refusez explicitement la lecture de **Salary** :

```sql
DENY SELECT ON dbo.sales_fincorp
(
    Salary
)
TO [participant@contactemeraudeit.onmicrosoft.com];
GO
```

4. Contrôlez les permissions enregistrées :

```sql
SELECT
    principal.name AS PrincipalName,
    permission.state_desc AS PermissionState,
    permission.permission_name AS PermissionName,
    OBJECT_SCHEMA_NAME(permission.major_id) AS SchemaName,
    OBJECT_NAME(permission.major_id) AS ObjectName,
    column_definition.name AS ColumnName
FROM sys.database_permissions AS permission
INNER JOIN sys.database_principals AS principal
    ON permission.grantee_principal_id = principal.principal_id
LEFT JOIN sys.columns AS column_definition
    ON permission.major_id = column_definition.object_id
    AND permission.minor_id = column_definition.column_id
WHERE principal.name = 'participant@contactemeraudeit.onmicrosoft.com'
  AND OBJECT_NAME(permission.major_id) = 'sales_fincorp'
ORDER BY column_definition.column_id;
```

**Ce que vous devez voir** :

- Les colonnes autorisées possèdent une permission **GRANT SELECT** pour le participant.

- La colonne **Salary** possède une permission **DENY SELECT**.

- Aucun rôle sémantique **BA_Europe** et aucun script TMDL ne sont nécessaires.

---

## Étape 3 — Tester les colonnes autorisées

**Objectif** : Confirmer que le participant peut lire toutes les lignes avec les colonnes autorisées, mais ne peut pas lire la colonne Salary.

**Actions participant — colonnes autorisées** :

1. Connectez-vous au **SQL analytics endpoint** avec le compte **participant**, dans l’éditeur Fabric ou dans SSMS.

2. Exécutez la requête suivante :

```sql
SELECT
    Region,
    COUNT(*) AS TransactionCount,
    SUM(Amount) AS TotalAmount

```

3. Vérifiez que la requête réussit et retourne les régions **Afrique**, **Asie** et **Europe**, soit les **300 transactions** et un montant total de **7 099 330,37**.

**Ce que vous devez voir avec participant** :

- La requête réussit et retourne les trois régions, car aucune politique RLS n’est plus active.

- Le participant peut utiliser les colonnes explicitement autorisées dans une projection, un filtre ou une agrégation.

---

## Étape 4 — Tester la colonne refusée

**Objectif** : Vérifier que toute requête qui tente de lire **Salary** est bloquée pour le participant.

**Actions participant** :

1. Dans la même session SQL ouverte avec le compte **participant**, exécutez :

```sql

    SalesRep,
    Salary
FROM dbo.sales_fincorp;
```

2. Essayez ensuite :

```sql
SELECT TOP 10 *
FROM dbo.sales_fincorp;
```

**Ce que vous devez voir avec participant** :

- La requête qui référence **Salary** échoue avec un message indiquant que la permission `SELECT` est refusée sur cette colonne.

## Étape 5 — Comparer les résultats avec le compte dev

**Objectif** : Confirmer que le refus appliqué au participant ne modifie pas les droits du compte **dev**.

**Actions formateur (compte dev)** :

## Étape 6 — Étendre la protection à toute la table avec l’OLS

**Objectif** : Passer d’une restriction ciblée sur la colonne **Salary** à une interdiction de lecture portant sur toute la table **dbo.sales_fincorp**.

> Pour isoler clairement l’effet de l’OLS de table, il faut d’abord retirer les permissions explicites accordées ou refusées au niveau des colonnes pendant le test CLS.

**Actions formateur (compte dev) — nettoyer la CLS** :

1. Dans l’éditeur SQL de Fabric ou dans SSMS, reconnectez-vous avec le compte **dev**.

2. Retirez les autorisations accordées sur les colonnes fonctionnelles :

```sql
REVOKE SELECT
ON OBJECT::dbo.sales_fincorp
(
    TransactionID,
    Region,
    SalesRep,
    Amount,
    ClientName,
    Date
)
FROM [participant@contactemeraudeit.onmicrosoft.com];
GO
```

3. Retirez le refus appliqué à la colonne **Salary** :

```sql
REVOKE SELECT
ON OBJECT::dbo.sales_fincorp (Salary)
FROM [participant@contactemeraudeit.onmicrosoft.com];
GO
```

4. Avec le compte **participant**, exécutez cette requête de contrôle :

```sql
SELECT TOP 10
    Region,
    SalesRep,
    Salary
FROM dbo.sales_fincorp;
```

La requête doit de nouveau réussir. Le participant est revenu aux permissions initiales obtenues par son rôle **Workspace Viewer**.

**Actions formateur (compte dev) — appliquer l’OLS à la table** :

1. Refusez la lecture de toute la table au participant :

```sql
DENY SELECT
ON OBJECT::dbo.sales_fincorp
TO [participant@contactemeraudeit.onmicrosoft.com];
GO
```

2. Contrôlez la permission enregistrée :

```sql
SELECT
    principal.name AS PrincipalName,
    permission.state_desc AS PermissionState,
    permission.permission_name AS PermissionName,
    OBJECT_SCHEMA_NAME(permission.major_id) AS SchemaName,
    OBJECT_NAME(permission.major_id) AS ObjectName,
    permission.minor_id AS ColumnId
FROM sys.database_permissions AS permission
INNER JOIN sys.database_principals AS principal
    ON permission.grantee_principal_id = principal.principal_id
WHERE principal.name = 'participant@contactemeraudeit.onmicrosoft.com'
  AND OBJECT_NAME(permission.major_id) = 'sales_fincorp';
```

La permission attendue est **DENY SELECT** avec `ColumnId = 0`, ce qui indique que le refus porte sur la table entière et non sur une colonne particulière.

**Actions participant** :

1. Reconnectez-vous au point de terminaison SQL avec le compte **participant**.

2. Essayez de lire une seule colonne non sensible :

```sql
SELECT TOP 10 Region
FROM dbo.sales_fincorp;
```

3. Essayez ensuite de lire toute la table :

```sql
SELECT TOP 10 *
FROM dbo.sales_fincorp;
```

**Ce que vous devez voir** :

- Les deux requêtes échouent, y compris celle qui ne demande que **Region**.

- Le participant ne peut plus lire aucune colonne de **dbo.sales_fincorp**.

- Le compte **dev** peut toujours interroger la table complète.

**Nettoyage final par le formateur (compte dev)** :

1. Retirez le refus appliqué à la table :

```sql
REVOKE SELECT
ON OBJECT::dbo.sales_fincorp
FROM [participant@contactemeraudeit.onmicrosoft.com];
GO
```

2. Avec le compte **participant**, réexécutez `SELECT TOP 10 Region FROM dbo.sales_fincorp;` et vérifiez que la lecture fonctionne de nouveau.
