# Workshop 1: Multi-source dynamic ingestion with validation

## Context: Optimizing a renewable energy supply chain

A **traditional production plant** decides to migrate to a solar-windian hybrid model. Energy data comes from multiple sensors and systems (current consumption, solar production, wind production, battery storage).

### 1. Status

- **3 daily data sources**:
  - `besoins_energetiques.csv` (consommation horaire de l'usine)
  - `production_solaire.csv`(return of panels per area)
  - `production_eolienne.csv`(turbine data)
- **Unstructured deposit**: files placed manually in a folder
- **Absence of validation**: impossible to know if all sources have arrived
- **Manual process**: a technician checks and imports files in Excel

### 2. Issue

How to automate the ingestion of heterogeneous energy data to analyse current needs and identify available renewable sources, without manual intervention and with validation of completeness?

Contraintes :

- Dynamically detect which files are present
- 
- Create a Bronze table by energy source
- 

### 3. Solution : Pipeline d'ingestion intelligent

Pipeline that scans, filters, copies and automatically tracks all energy sources to Bronze.

# Tip: Import and export and a JSON pipeline

## Objective

- Understand that a Fabric pipeline is a **JSON file** (`pipeline-content.json`).
- The **Save / Version / Duplicate** out of the interface.
- The **reimport** into the same workspace or another, and know what to reconnect.

## A. Export pipeline

1. Ouvrir `PL_Ingestion_Energie_Bronze`in the pipeline publisher.

2. Tab **Home** of the toolbar: click on the icon **Export** (arrow to the right, between *Save as* and *Import*).

3. The browser downloads a **file`.zip`** appointed from pipeline
   
    (`PL_Ingestion_Energie_Bronze.zip`) on your **PC** 
   
   (default folder *Downloads*).

4. Move it to a work folder, e.g.`Module 3 Les piplines ms fabric/exports/`, to find him easily at the import.

5. Alternative read-only: display the pipeline JSON code (tab **View**, *JSON code* option) **[to be checked]**.

Please note: exact zip content (files present, including`pipeline-content.json`).

## B. Read JSON

Ouvrir `pipeline-content.json`in an editor. Find:

- **`properties.activities`**: one entry per activity (`ScanLanding`, `BouclerFichiers`, then inside`EstCSV`, `CopierVersBronze`, `TracerFichier`, `RecupererTracage`).
- **`type`** : `GetMetadata`, `ForEach`, `IfCondition`, `Copy`, `AppendVariable`, `SetVariable`.
- **`dependsOn`**: the execution order (green/red arrows of the canvas = conditions`Succeeded`/`Failed`).
- **Expressions** : objets `{"value": "@item().name", "type": "Expression"}`.
- **`properties.variables`** : `FichiersTraites`, `FichierActuel`, `NombreFichiers`, `FichiersTemp`.
- **References to lakehouse**:`workspaceId`,`artifactId`,`rootFolder`(`Files`in source,`Tables`destination). **These identifiers change from workspace to workspace. **

## C. Create a test pipeline and import the zip exported from the PC

The import is made **from the publisher of a pipeline**, with the icon **Import** on the **Home** tab (arrow to the bar, right of *Export*). It is applied to an empty **pipeline test** in order not to touch the original.

1. In`WS_Energie_Renouvelable` : **+ New item → Data pipeline**, nom `PL_Test_Import`(empty pipeline, canvas without activity).
2. In its editor, tab **Home** → **Import**.
3. A **File Upload** box opens: navigate to the Step A folder and select **`PL_Ingestion_Energie_Bronze.zip`** (the zip already exported).
4. The **model (template)** screen displays: pipeline preview (Get Metadata)`ScanLanding` → ForEach `BouclerFichiers` → `EstCSV`), description ("Ingestion of CSV Landing to Bronze Tables") and section **Inputs**.
5. In **Inputs**, the **Lakehouse *** field (*For ScanLanding (GetMetadata), EstCSV (IfCondition)*) is mandatory: it offers *No results found* as long as no connection is chosen. Click **Browse all** (or update button) and select **`LH_Energie_Bronze`**, the lakehouse that contains the data.
6. Validate import (screen confirmation button, wording **[to be checked]**).
7. Control the canvas: 2 activities at the root,`EstCSV`in ForEach with its 3 internal activities; tab Home → **Validate** without error; variables present (`FichiersTraites`, `FichiersTemp`, …).

**Change exercise (optional)**: before step 3, open zip, edit`pipeline-content.json`in a *copy* (e.g.`"retry": 0` → `"retry": 2`on`CopierVersBronze`), compress with the same tree, then import; Then check Retry = 2 in the Settings tab of the activity.

## D. Controls

- Visually compare the imported pipeline with the original (same activities, same dependencies, same expressions).
- Check the modification of step C (e.g. **Retry = 2** in the Settings tab of`CopierVersBronze`).
- **Do not launch** the imported pipeline without cleaning: the destination is **Append**, one run would add another 30 lines per table (doubles). If desired: empty Bronze tables before or accept duplicates for illustration.

## E. Use case to be retained

- **Sauvegarde / versionment Git** : the JSON is legible and comparable (diff).
- **Duplication / environments** (Dev → Test → Prod): reimport and reconnect sources (the`workspaceId`/`artifactId`point to another workspace). Fabric's **deployment pipelines** automate this.
- **Generation by script/API**: a pipeline can be created by sending this JSON (encoded in Base64) to the REST Fabric API (`definition.parts`) : this is the method used for automation.

# Tip: Plan and monitor the pipeline in Monitor

## Objective

- Run`PL_Ingestion_Energie_Bronze`**automatically** at regular intervals.
- Find and analyze these executions in the hub **Monitor** (left menu).

## Before you start: pay attention to the Append

The destination of Copy data is **Append**: each execution add 30 lines per table. For the financial year:

- planning a period **short** (some executions);
- **disable or delete** planning at the end;
- then count the lines (30 × number of runs + 30): this is the starting point of the discussion about**idemance** (Overwrite, or incremental logic).

## 1. Creating Planning

1. Ouvrir `PL_Ingestion_Energie_Bronze`.
2. Tab **Home** → **Schedule**, then **Add Schedule**.
3. Select type: **Fixed schedule** (minute/hour/day/week/month frequency). *The **Interval-based schedule** option exists in preversion: not used here. *
4. Renseigner :
   - **Repeat/frequency**: every **5 minutes** (for testing);
   - **Start date and time**: in 2-3 minutes;
   - **End date and time**: about 15 minutes after the start;
   - **Time zone** : fuseau de Paris ;
   - activation switch: **activated**. **[exact labels to be observed]**
5. **Save**.

Documentation rules:

- a **start and end dates are mandatory**: there is no endless planning (for a permanent execution, put a very distant date, e.g.`01/01/2099 12:00 AM`) ;
- up to **20 planning** per pipeline, each with its frequency and dates;
- ** pipeline parameters** may receive values at each planned execution (names identical to those of the pipeline); not used here;
- **Failure to notify** (same panel): e-mail notification to users/groups **in case of failure of a planned run** (never for a manual run).

## 2. Follow executions in pipeline

- Tab **Home** (or **Run**) → **View run history** : list of executions of this pipeline.
- Wait for the start time: a new line appears at each interval.

## 3. Track execution in Monitor

1. Left menu → **Monitor** (Manric's monitoring hub; you only see the items you have access to).
2. Page **Job runs**.
3. Filter: **time range** (last hour, 6 a.m., 24 h.m., N days), **Type item** = Data pipeline, **Status** (In progress, Followed, Failed, Cancelled), **Workspace**, or search by name (`PL_Ingestion_Energie_Bronze`).
4. Documented columns: **Item name**, **Last run status**, **Average duration**, **Last run details**. Additional columns via **Manage view → Column Options**. **[note: column indicating planned / manual and its wording]**
5. Click on an execution: the **detail panel** displays the history; for a pipeline: execution flow, activity table and Gantt diagram. Icons **Open detail page** (full page) and **Open item** (back to editor); button **Refresh**.
6. In case of failure: button **Investigate** (agent Operations, preversion — see note below).

## 4. Managing planning

- **Home → Schedule**: Change, or enable/disable with the switch.
- Delete: icon **Edit** (crayon) → **Delete schedule** at the bottom of the panel.
- The *Interval-based* pre-version arrays are neither editable nor deactivated: deletion/recreation.

## 5. Check the effect on tables (Appendix)

After the executions, count the lines of each table in the lakehouse: the total increases by 30 at each run. Conclusion: a planned pipeline must be **idepotent** (Overwrite for full loading, or filtering of previously processed files).

# Section : remplacer Copy data par Copy job

## Objective

Perform the same ** Bronze** load with Copy data then with Copy job, and compare. The original pipeline is **unmodified**: work on a copy, and tables of the variant are suffixed`_cj`.

## Principe

- **Copy data**: *parameter* activity of a pipeline; only one activity serves the 3 files thanks to`@item().name`.
- **Copy job** : *autonomous item* from workspace ; ** first create and configure it** (source, destination, copy mode), then select it in an activity **Copy job**.
- **Limit found**: Copy job activity (General tabs and Settings) does not offer ** neither parameter nor filename field**; she designates **a specific Copy job**. The stored JSON contains only`copyJobId`, `workspaceId`and`operationType: "RunCopyJob"`. Hence: **a Copy job per file**, referred by an activity **Switch** on`@item().name`.

## Traps

- The Copy job must **exist and be configured** before being selected in the pipeline.
- **Append + multiple runs = duplicates** ; Here **Overwrite** is used.
- Schedule of the pipeline **and** schedule of the Copy job active : double executions ; keep only one owner of the orchestration (the pipeline).
- No documented output of the Copy job (e.g. copied lines) usable in expression:`TracerFichier`based on`@item().name`.

## Part 1: Create and configure 3 Copy jobs

| Copy job                  | Source (`LH_Energie_Bronze`/`Files/landing`) | Destination (Tables)      |
| ------------------------- | ---------------------------------------------- | ------------------------- |
| `CJ_Besoins_Energetiques` | `besoins_energetiques.csv`                     | `besoins_energetiques_cj` |
| `CJ_Production_Solaire`   | `production_solaire.csv`                       | `production_solaire_cj`   |
| `CJ_Production_Eolienne`  | `production_eolienne.csv`                      | `production_eolienne_cj`  |

- Copy data is suitable for ingestion **controlled by metadata** (list of files or dynamic tables,`ForEach`, expressions).
- Copy job is suitable for a **simple and sustainable** copy (Bronze, bulk, incremental, CDC) with less plumbing.
- Capacity: Full  check with the **Capacity Metrics app**. No "always cheaper or faster".

## Variante hors boucle

A **only** Copy three match job, invoked **only once** after`ScanLanding`Without ForEach or If. Simpler and more representative of the product, but loop and traceability lose their usefulness.

> Avoid: a unique Copy job **in** The ForEach: it would copy the 3 files at each iteration.

# Section: Ingestion from a REST API (Copy data)

## Objective

Replace reading CSV files (`GetMetadata` → `ForEach` → `If Condition` → `Copy data`) by reading three ** HTTP endpoints** with a single **Copy data** REST source activity, controlled by a parameter.

## Prerequisite

- Bronze tables already exist (`besoins_energetiques`, `production_solaire`, `production_eolienne`) : all columns are in`string`.
- The API service (Azure Function, anonymous, GET) is provided: the learner only has the termination points.

## Attention points

- **Ne pas relancer sans vider** : doublons en Append.
- **Pagination**: not used here (30 lines per endpoint); a bulky real API requires "growling rules* in the source.
- **Authentification**: The Pedagogical API is anonymous; in production, prefer authentication (Main Service, Basic, etc.) and never put a secret in the JSON.
- **Typage**: intentionally postponed to Silver.

| Endpoint                                                                      | Bronze table           | Lines |
| ----------------------------------------------------------------------------- | ---------------------- | ------ |
| `https://func-energie-api-1ae13f08.azurewebsites.net/api/besoins`             | `besoins_energetiques` | 30     |
| `https://func-energie-api-1ae13f08.azurewebsites.net/api/production-solaire`  | `production_solaire`   | 30     |
| `https://func-energie-api-1ae13f08.azurewebsites.net/api/production-eolienne` | `production_eolienne`  | 30     |

Endpoint`/api/health`verify that the service is responding.

2. Note: JSON response = array of objects, one key per column (same names as CSV), numerical JSON numbers, ISO text dates.

3. **Create**. Then open the connection settings and note the **ID Connection** (GUID).

## Part 3 – Import Pipeline

1. Create an empty test pipeline (e.g.`PL_Test_REST`).
2. **Import/Export** → **Import pipeline** → file`PL_Ingestion_Energie_Bronze_REST.json`(folder`case study 1 data`).
3. If file still contains`<REST_CONNECTION_ID>`, replace it with the GUID of the connection before import.
4. Ouvrir `BouclerEndpoints` → `CopierRestVersBronze` → onglet **Source** :
   - **Connect**: If an error "Failed to load the connection" appears, select **Rest** from the list.

## Part 4 – Understanding the pipeline

| Element                                  | Role                                                                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Parameter`Endpoints` (Array)            | Liste de 3 objets `{ relativeUrl, table, mappings }`: one per source                                                              |
| `BouclerEndpoints`(ForEach, sequential) | Go through the list; sequential because variables are not thread-safe                                                          |
| `CopierRestVersBronze`(Copy data)       | REST Source: **Related URL** =`@item().relativeUrl`; destination: table =`@item().table`; **Mapping** =`@item().mappings` |
| `TracerFichier` / `RecupererTracage`     | Keep track of fed tables (variable`FichiersTemp`, `FichiersTraites`)                                              |

Key Points:

- **One** Copy data for three sources: add source = add object in`Endpoints`.
- **Explicit table mapping**: an API returns JSON objects, mapping combines`$['Colonne']`→ table column.
- **Types**: source`Double`for numbers, but destination`String`, because Bronze tables are completely in`string`. The typing (dates, decimals) is done in **Silver**.

## Part 5 – Run and verify

1. **Vider front Bronze tables** (mode is **Append**: restart without emptying gives 60 lines instead of 30).
2. **Run** of the pipeline.
3. In the execution view: 3 iterations of`CopierRestVersBronze`in ForEach, all **Followed**.
4. In Lakehouse: 30 lines per table, columns in`string`.

## Comparison of the two approaches

|                        | CSV files                               | REST API                       |
| ---------------------- | ------------------------------------------ | ------------------------------ |
| Source                 | Lakehouse files (landing)            | Endpoints HTTP                 |
| Discovery of sources | `GetMetadata` + `ForEach` + `If Condition` | Liste `Endpoints`(parameter)  |
| Mapping                | Automatique (CSV tabulaire)                | Explicite (JSON)               |
| Authentification       | Aucune (Lakehouse)                         | Connexion Web v2               |
| Nouvelle source        | File                         | Add an object to`Endpoints` |

### Insight 1: Preliminary energy balance


** Interpretation**:

- **86% energy autonomy** with renewable sources
- **14% deficit** to be filled (traditional network or batteries)
- **Objective achieved**: Significant reduction in network dependence
