---

## The objective of the workshop

The Bronze layer of a Medallion represents the first stage of data processing.

Why this approach? The Bronze layer acts as a **source of unchangeable truth**. It preserves data exactly as it comes from sources

## Business context

Your organisation operates a network of six electricity production and consumption sites in France.

1. Two industrial sites (capacity 5 MW and 3.5 MW), 

2. Two commercial sites (2 MW and 1.5 MW) 

3. Two residential units (0.8 MW and 0.6 MW). 

Each site is equipped with IoT sensors that transmit electricity consumption every 15 minutes for 30 days. 

Additional data come from several sources: 

1. EPEX market spot price, 

2. Weather conditions, 

3. Reference data of maintenance sites and events.

**The problem:** 

These raw data arrive in various formats (incoherent timestamps, missing or invalid numerical values represented by error codes such as -888 or -999), with duplicates and uneven quality depending on the source. Before using this data for analysis or machine learning, it is necessary first to centralize it, preserve its integrity, and document anomalies. That's exactly the role of the Bronze Layer.

## Cell 2: Import consumption raw.csv → Delta Table

### Before executing

Load the first source file,`consumption_raw.csv`, which contains electricity consumption data captured every 15 minutes.

 PySpark offers API`spark.read.format("csv")`ideal for loading CSV. 

Options`header=true`and`inferSchema=true`instruct Spark to treat the first line as a header and automatically deduce column types (timestamp, integer, string, etc.). 

After reading DataFrame, you write data in Delta format (format optimized for data lakehouse) in the schema`bronze`. 

Fashion`overwrite`crush any existing table with the same name, ensuring a complete reset at each run.

Line counting (`count()`) is a critical step:

 In data engineering, it is systematically checked that the number of lines loaded corresponds to the waiting. A major divergence would indicate a reading or truncation problem.

### 💻 Code

```python
# Charger le CSV avec PySpark
df_consumption = spark.read.format("csv") \
    .option("header", "true") \
    .option("inferSchema", "true") \
    .load("Files/data_bronze_notebooks/consumption_raw.csv")

# Compter les lignes avant écriture
nb_lignes = df_consumption.count()

# Créer la table dans le schéma bronze
df_consumption.write.mode("overwrite").format("delta").saveAsTable("bronze.consumption_raw")

print(f"✅ Table bronze.consumption_raw créée : {nb_lignes} lignes")
```

### Results

```
✅ Table bronze.consumption_raw créée : 18144 lignes
```

### Interpretation

- **18 144 lines** loaded, or 17,280 theoretical (6 sites × 4 measurements/h × 24 hours × 30 days) + 864 duplicates
- **Table Delta**`bronze.consumption_raw`: persistent and queryable in SQL
- **Source of truth**: data stored as such, without transformation

## Cell 4: Consumption raw quality diagnostic

### Before executing

You now perform a statistical diagnosis of the table`consumption_raw`. This aggregate SQL query has several quality dimensions: the total number of rows, the number of unique combinations (timestamp, site id) to detect duplicates, null values (total absence), negative values (error codes), and outliers (consumption > 10 MW, abnormally high). These metrics form the quality line base for the Bronze layer and will serve as a benchmark to assess the impact of Silver cleaning.

### 💻 Code

```sql
%%sql
-- Compter les NULL, codes erreur, doublons
SELECT
    COUNT(*) as total_rows,
    COUNT(DISTINCT timestamp, site_id) as unique_rows,
    COUNT(*) - COUNT(DISTINCT timestamp, site_id) as duplicates,
    SUM(CASE WHEN consumption_mw IS NULL THEN 1 ELSE 0 END) as null_values,
    SUM(CASE WHEN consumption_mw < 0 THEN 1 ELSE 0 END) as error_codes,
    SUM(CASE WHEN consumption_mw > 10 THEN 1 ELSE 0 END) as outliers
FROM bronze.consumption_raw
```

### Results

| total_rows | unique_rows | duplicates | null_values | error_codes | outliers |
| ---------- | ----------- | ---------- | ----------- | ----------- | -------- |
| 18144      | 17280       | 864        | 554         | 319         | 27       |

### Interpretation

- **864 duplicates** (4.8%): network retransmissions or sensor recalibration, to be deduced in Silver
- **554 NULL** (3%): sensor or maintenance failure, to be filtered or charged
- **319 error codes** (1.8%):`-888`sensor defect,`-999`network failure,`-777`calibration
- **27 outside** (0.15 %): consumption > 10 MW while the maximum capacity is 5 MW, to be investigated
- **Baseline quality**: these figures will be used as a reference to measure the effect of Silver cleaning

### Technical key points

**Idemotence**: Controls`CREATE SCHEMA IF NOT EXISTS`and mode`overwrite`ensure that re-executing the notebook does not create errors or duplicates. This is essential in production.

**Spark API** : You have combined the PySpark API (reading CSV, count, write) and SQL (SELECT, CUNT DISTINCT, CASE WHEN aggregations). Both models coexist in Fabric; choose according to readability and performance.
