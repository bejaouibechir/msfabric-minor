---

## Issue

Complete processing unnecessarily rereads all files, consumes more capacity and can introduce duplicates. Continued active treatment would be disproportionate for some periodic deposits.

So you have to build a limited job: at each launch, it processes everything that is available, remembers its progression, then stops and releases Spark resources.

Treatment must be resistant to repeats. A restart without new file must read zero new line. A recovery after failure shall not duplicate the data already written.

The solution contains three scripts:

| File | Role |
|---|---|
| `traitement_capteurs.py` | incremental reading, quality, MERGE and audit |
| `capteurs_sjd_utils.py` | Pure standardization and validation, Spark scheme |

The key to the Silver table is`capteur_id + timestamp + grandeur`. It assumes that a sensor only publishes a value of the same magnitude at the same time. In a real system, an immutable measurement ID or sequence number is preferable.

## Step 4 — Normalize timestamps

The generator produces two formats:

```text
2025-02-01T00:00:00Z
01/02/2025 00:00:00
```

The pure module successively tries both formats and returns a`datetime`UTC. In Spark, use`coalesce` :

```python
timestamp_normalise = F.coalesce(
    F.to_timestamp("timestamp", "yyyy-MM-dd'T'HH:mm:ssX"),
    F.to_timestamp("timestamp", "dd/MM/yyyy HH:mm:ss"),
)
```

A correctly recognized heterogeneous date is not rejected. A string that does not match any format receives the pattern`TIMESTAMP_INVALIDE`.

Local control normalized the expected 55 heterogeneous timestamps.

## Step 6 — Configure the Sustainable Checkpoint

Use a separate location for this request:

```text
Files/checkpoints/sjd2_capteurs
```

Checkpoint keeps already processed files, offsets, metadata and stream status. Never share it with another request.

The removal or corruption of the checkpoint breaks the recovery contract. With a new checkpoint, the file source can be reread from the beginning. MERGE then limits duplicates in tables, but the cost of recalculation remains.

The relative path is solved in the default Lakehouse of Spark Job Definition. The actual presence of the file after the first run remains`[à constater]`.

## Step 7 — Use`foreachBatch`and`availableNow`

💻 **Code**

```python
requete = (
    flux.writeStream
        .queryName("sjd2-capteurs-available-now")
        .foreachBatch(traiter_batch)
        .option("checkpointLocation", args.checkpoint_path)
        .trigger(availableNow=True)
        .start()
)
requete.awaitTermination()
```

`availableNow`processes all available data at launch, validates the checkpoint, and then stops the query.`awaitTermination()`is essential: without it, the Spark Job Definition could reach a terminal state while the stream still works asynchronously.

This mode is different from a continuous stream: it avoids keeping an active Spark session between two file arrivals.

The Fabric documentation confirms the use of`availableNow`for an incremental job planned and running Structured Streaming in a Spark Job Definition.

## Attention

### Cost, capacity F2 and checkpoint

Each launch heats a Spark session.`availableNow`free the calculation after the backlog, but several jobs can be queued. Consumption remains`[à constater]`. A checkpoint belongs to a single query: do not copy or delete it without analyzing compatibility and preparing the replay.

### Order of arrival

The file source discovers the new files, but their order should not carry an implicit business rule. The key and timestamps must be sufficient to make the deterministic result.

### Idempotence

Checkpoint reduces rereading; it is not a substitute for the sink. One`foreachBatch`can be replayed. The MERGE on deterministic keys protect the tables.

### Authentification

Use the user's local identity and a managed identity or a controlled service principal for hosted automation. Never insert a token into the arguments or variables of a pipeline.
