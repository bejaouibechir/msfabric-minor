### 1.7 - **Schedule**: Combination Roles Workspace × Item Permissions on Lakehouse

The starting position before applying the new set of permissions

This section is one of the most important of the workshop. Workspace and item permissions are not two independent systems: they ** influence each other**, and the observed result is not always intuitive. The tests below were performed in real-life conditions on an active Fabric holding.

> Note**: actual behaviour may differ from what would logically be expected. This is precisely the educational interest of this chessboard.

#### Real Observations Matrix (Lakehouse)

| Workspace role  | Permissions granted (Lakehouse + Notebook)                                                 | Bouton Run Notebook  | SQL Analytics Endpoint Access | Lakehouse Interface Access | Overall level observed      | Educational commentary                                                     |
| --------------- | -------------------------------------------------------------------------------------------- | -------------------- | ---------------------------- | ------------------------- | -------------------------- | --------------------------------------------------------------------------- |
| **Viewer**      | `Read`+`ViewOutput`                                                                        | ❌                    | ✅                            | Limited                    | SQL Play Only      | Very restrictive — tables inaccessible without`ReadAll`                       |
| **Viewer**      | `Read` + `ViewOutput` + `ReadAll` + `Execute` / Notebook : `Read` + `Edit` + `Run`           | *(or very late) * | ✅                            | Limited                    | SQL playback OK, Run blocked | **Even with all rights item + Notebook, the Viewer role blocks Run** |
| **Contributor** | `Read` + `Write` + `Reshare` + `Execute` + `ReadAll` + `ViewOutput` / Notebook : tous droits | *(after latency) *  | ✅                            | ✅                         | Good balance              | The most stable role for demos — to be given priority in training             |
| **Member**      | `Read` + `Write` + `Reshare` + `Execute` + `ReadAll` + `ViewOutput` / Notebook : tous droits | ✅                    | ✅                            | ✅                         | Extended access               | **Can run the Notebook and access SQL Analytics Endpoint**          |
| **Admin**       | All rights inherited                                                                          | ✅                    | ✅                            | *(create / delete) *   | Total access                | Comportement normal d'administrateur                                        |

#### Some remarks to memorize before starting with Lakehouse permissions

**1 — Changing roles can reset granular permissions. **  
Pass a user of`Viewer`to`Contributor`or`Member`can overwrite already configured item permissions. Revalidate systematically after each change of role.

**2 — `ReadAll` + `Execute`focus on SQL Analytics Endpoint. **  
These permissions guarantee access to SQL Endpoint but do not guarantee the execution of Notebooks. Spark and SQL plans have separate authorisation mechanisms.

**3 — The role`Member`allows the two main uses. **
With permissions indicated in the matrix, a`Member`can run the Notebook with the **Run** button and access the **SQL Analytics Endpoint**.

**4 — `Contributor`is the role to be recommended in the context of training. **  
Better balance between Notebook access, SQL access and item management, without administrative rights.

#### 1.7.1 Scenario 1 – Baseline (as clean as possible)

**Tested configuration:**

- Role Workspace: **Viewer**
- Lakehouse Permissions: **Read + ViewOutput** Only

**Observed result:**

- The test account can open the Lakehouse.
- It can open the **SQL analytics endpoint** and run queries.
- It can see the data via the SQL endpoint (SELECT * FROM ... works).
- On the other hand, in the Lakehouse interface (Tables / Files), it can neither see nor manipulate data easily.

**Conclusion:** With minimum permissions (Read + ViewOutput), access via SQL endpoint is already possible, but experience remains limited outside the SQL.

### 1.7.2 Scenario 2 – Adding ReadAll

**Tested configuration:**

- Role Workspace: **Viewer**
- Lakehouse Permissions: **Read + ViewOutput + ReadAll + Execute**

**Observed result:**

- No significant change from Scenario 1.
- The test account continues to be able to execute queries in the SQL endpoint and view the data.
- Adding ReadAll did not change the behavior in this regard for SQL endpoint.

**Conclusion:** In this environment, Read only is already enough to read data via SQL analytics endpoint. ReadAll does not bring visible benefits in this specific context.

### 1.7.3 Scenario 3 – Test via Spark (Notebook)

**Tested configuration:**

- Role Workspace: **Viewer**
- Lakehouse Permissions: **Read + ViewOutput + ReadAll + Execute**

**Observed result:**

- In a Notebook attached to the Lakehouse, the **Run** button is **not visible**.
- The test account cannot run the Notebook, even with ReadAll and Execute granted on the Lakehouse.

**Conclusion:** ReadAll and Execute on Lakehouse allow access via SQL, but not enough to run a Notebook.

#### 1.7.4 Scenario 4 – Added rights to the Notebook (Viewer)

**Tested configuration:**

- Role Workspace: **Viewer**
- Lakehouse Permissions: Read + Write + Reshare + Execute + ReadAll + ViewOutput
- Permissions on the Notebook : Read + Edit + Share + Run

**Observed result:**

- Despite all the rights granted on the Notebook, the **Run** button remains invisible or does not appear.
- The test account still cannot run the Notebook.

**Conclusion:** With the role **Viewer**, even giving all possible permissions on the Notebook, execution remains blocked. Workspace is the limiting factor.

#### 1.7.5 Scenario 5 – Contributor Passage

**Tested configuration:**

- Role Workspace: **Contributer**
- Lakehouse Permissions: Read + Write + Reshare + Execute + ReadAll + ViewOutput
- Permissions on the Notebook : Read + Edit + Run

**Observed result:**

- The **Run** button in the Notebook becomes visible (sometimes after refreshment or latency).
- The test account can now run the Notebook cells successfully.
- SQL endpoint access remains available.

**Conclusion:** The role **Contributer** unlocks the execution of Notebooks. This is currently the most stable role for practical demonstrations.

#### 1.7.6 Scenario 6 – Member Passage

**Tested configuration:**

- Role Workspace: **Member**
- Permissions on the Lakehouse : Read + Write + Reshare + Execute + ReadAll + ViewOutput + SubscribeOneLakeEvents

**Observed result:**

- The **Run** button in the Notebook is visible and allows you to run the cells.
- The **SQL Analytics Endpoint** is accessible.
- The Lakehouse interface (Tables / Files) is visible and accessible.

**Conclusion:** With the role **Member** and the permissions indicated, the user can both run the Notebook and use the SQL Analytics Endpoint.

#### 1.7.7 Scenario 7 – Passage to Admin

**Tested configuration:**

- Role Workspace: **Admin**
- Permissions on Lakehouse : Read + Write + Reshare + Execute + ReadAll + ViewOutput + ...

**Observed result:**

- The **Run** button is visible.
- The SQL Analytics Endpoint is accessible.
- Full access to the Lakehouse interface (see, create, delete tables, etc.).

**Conclusion:** The role **Admin** gives full access, as expected.

## Part 5 - DB roles: Build-in and Custom in Warehouse

Database roles (**DB roles**) are an intermediate security layer between granular SQL permissions (individual GRANT/DENY seen in Part 4) and workspace management. They allow **group permissions under a name** and assign users to this group rather than manage rights one by one.

Microsoft Fabric Warehouse exhibits the same fixed roles as SQL Server, which can be accessed in the Explorer under **Security > DB roles (Built-in)**. It also allows to create **custom role** via`CREATE ROLE`.

> **Official reference**: [SQL granular permissions in Microsoft Fabric](https://learn.microsoft.com/en-us/fabric/data-warehouse/sql-granular-permissions) — [Database-Level Roles (SQL Server)](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/database-level-roles)

### 5.1. - Present the DB Build-in roles of the Warehouse

#### Visible roles in the explorer

| Role Build-in       | Permissions effectives                                      | Relevance to Fabric                                         |
| ------------------- | ----------------------------------------------------------- | -------------------------------------------------------------- |
| `db_owner`          | Total control : DDL, DML, security, configuration          | Complete — reserved for directors                          |
| `db_accessadmin`    | Manages the addition/deletion of users in the database        | Limited — no SQL auth in Fabric (Entra ID only)   |
| `db_securityadmin`  | GRANT / DENY / REVOKE, role management (excluding fixed roles) | Helpful to delegate SQL security management              |
| `db_ddladmin`       | CREATE / ALTER / DROP of objects — without security rights    | Typical for an "architect data" role                         |
| `db_backupoperator` | Run BACKUP commands                               | Not applicable — BACKUP not available in Fabric (SaaS)   |
| `db_datareader`     | SELECT on all base tables and views             | Overall reading — attention to sensitive data              |
| `db_datawriter`     | INSERT / UPDATE / DELETE on all tables              | Global Writing — Restrict with DENY if necessary       |
| `db_denydatareader` | DENY SELECT explicit on all tables                 | Blocks any read access, even if`db_datareader`is granted |
| `db_denydatawriter` | DENY INSERT/UPDATE/DELETE on all tables             | Block all writing, even if`db_datawriter`is granted     |
| `public`            | Default role — all users are members     | Toujours actif — ne pas y mettre de permissions                |

> *Important Fabric**:`db_backupoperator`and`db_accessadmin`exist in the interface but have limited utility in Fabric.`db_backupoperator`in particular has no effect because orders`BACKUP`are not available in a Warehouse Fabric (SaaS managed platform). Mention them for informational purposes without using them in demonstrations.

#### Explanation: Role Workspace mapping → SQL permissions implicit in the Warehouse

In a Fabric Warehouse, the Workspace role is **not just an access control to the item** — it translates directly into SQL permissions inside the engine:

| Workspace role  | Implicit SQL Permissions in Warehouse            |
| --------------- | ------------------------------------------------------- |
| **Admin**       | Equivalent`db_owner`— total control                  |
| **Member**      | Reading + writing DML (SELECT, INSERT, UPDATE, DELETE) |
| **Contributor** | Reading + writing DML (SELECT, INSERT, UPDATE, DELETE) |
| **Viewer**      | Play only (SELECT only)                       |

A user **Contributor** has already written rights implicit in the Warehouse, **regardless of any DB role**. Add`db_datareader`to a Contributor does not restrict anything — on the contrary, the rights inherited from the workspace remain active.

> **Key rule**: in Fabric Warehouse, the Workspace role acts as a **floor of permissions**, not as a ceiling. A DB role cannot restrict what the Workspace role grants — only one`DENY`SQL explicit can.

### 5.9 - Comparaison : DB roles vs GRANT/DENY direct

| Criteria         | GRANT/DENY individual (Part 4)     | DB Roles (custom or build-in)                                |
| --------------- | ------------------------------------- | ------------------------------------------------------------ |
| Granularity     | Maximum — objet par objet             | Average — defined at role level                          |
| Maintenance     | Complex with many users | Simple — add/remove a member                           |
| Reusability | Faible                                | High — a role, N members                                  |
| Auditability    | Via `sys.database_permissions`        | Via `sys.database_role_members` + `sys.database_permissions` |
| Cas d’usage     | Very specific Permissions by User | Groupes de profils (analyst, writer, admin)                  |
| Conflit DENY    | Direct DENY > Role GRAND           | Role DENY > Role GRANT or direct                       |

> **Final Key Message**: in a Warehouse Fabric, the good practice is to **combine the two approaches**—use custom roles to manage the typical profiles, and add`DENY`for particularly sensitive exceptions or data (e.g.:`gold.margin_internal`).

### 6.1 - Create the predicate function

The predicate function is the **heart of the RLS mechanism**.

- **What she does**: for each line read in a protected table, Fabric calls this function by passing it the column value`Region`of this line.
  
  - The function returns`1`(= allow) if the connected user (`USER_NAME()`) in the table`security.user_region_access`for that region or`dev`(the trainer, who sees everything).
  
  - The function returns an empty table (= block) in all other cases.

- **What it is not**: it is not`un filtre classique`which is applied manually in queries. Once security policy is created in 6.2,
  
  Fabric injects **automatically and invisiblely** in each`SELECT`on protected tables — the user sees only the lines to which he is entitled, without even knowing that the filter exists.

- **The link with our data**: the table`security.user_region_access`(created in Part 3) contains mapping`participant → Nord`and`test → Sud`. It is this table that the function questions each reading to decide which lines are visible.
1. Open a new SQL query
2. Coller :

```sql
CREATE FUNCTION security.fn_region_predicate(@Region AS NVARCHAR(20))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS fn_region_predicate_result
    WHERE EXISTS
    (
        SELECT 1
        FROM security.user_region_access AS ura
        WHERE ura.UserPrincipalName = USER_NAME()
          AND ura.Region = @Region
    )
    OR USER_NAME() = 'dev@contactemeraudeit.onmicrosoft.com';
GO
```

3. Click on **Run**

| ----------------- | --------------------------------- |
| **Function name** | `security.fn_region_predicate`    |
| **Principe**      | Filter by region |

## Part 8 - Compare Workspace roles, item permissions and SQL permissions

### 8.1. - Raising the Workspace role of`test` (Viewer → Contributor)

The objective is to show that an increase in Workspace role **is not enough** to bypass a`DENY`SQL already in place.

1. With`participant` (Admin), ouvrir **Workspace settings → Manage access**
2. Localiser `test@contactemeraudeit.onmicrosoft.com`
3. Change its role from **Viewer** to **Contributer**
4. Enregistrer

| Compte                                   | Former role | New role |
| ---------------------------------------- | ----------- | ------------ |
| `test@contactemeraudeit.onmicrosoft.com` | Viewer      | Contributor  |

**What you need to see on screen**:

- The role`Contributor`displayed for`test`

> ** Expected result**:`test`now has higher Workspace rights — we'll check if it bypasses the DENY SQL of Part 7.

### 8.2 - Replay SQL tests after changing roles

1. With`test`(now Contributor), refresh the interface
2. Rejouer :

```sql

SELECT Region, City, CustomerName, ProductName, SalesAmount, CustomerTier
FROM gold.sales_secure_detail;

```

| Test                               | Expected result                                        |
| ---------------------------------- | ------------------------------------------------------- |
| Access to Bronze                     | Authorised (Contributer = Implicit DML)                  |

**What you need to see on screen**:

- The`DENY`on`CustomerEmail`holds — the Workspace role does not crush it

> **Expected result**: Key message is demonstrated — **DENY SQL is the only reliable barrier on a sensitive column**, regardless of the Workspace role.
