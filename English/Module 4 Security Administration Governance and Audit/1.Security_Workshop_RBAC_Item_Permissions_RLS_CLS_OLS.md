# Layer 1 — RBAC Workspace

## Step 1 — Assign Workspace Viewer Role to the Participant Account

**Objective**: Create a minimal Fabric environment, assign the role **Viewer** to the participating account and effectively verify the access granted by this role to a Lakehouse and its SQL termination point.

**Pourquoi** :  
Workspace Viewer is the only role that does not allow any dangerous modification or execution.

It constitutes the security ceiling for all end users.

| Role            | Main capacity                                                               | Access and Sharing Management                                                                          | Usage type                                       |
| --------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Admin**       | Has complete control over the workspace and its content.                        | Can add or remove all users                                                            | Owner or administrator of the platform. |
| **Member**      | Can create, edit, execute and delete objects and data from workspace. | May add **Members**, **Contributers** and **Viewers** in addition to contributory rights | Team Leader or Content Manager  |
| **Contributor** | Can, like a **Member**, create, edit, execute and delete objects        | Can't manage workspace roles or add users.                                    | Developer or designer                        |
| **Viewer**      | Can view the workspace content without changing it. .                          | Can't handle access.                                                                             | Reader, business analyst                         |

>

## Step 2 — Creating the Predicate Function and SLA Policy

**Objective**: Authorize the account **participant** to read only Europe lines while maintaining full access to the account **dev**.

**Actions formateur (compte dev)** :

1. Open a new query in **SQL analytics endpoint** from **LH FinCorp**.

2. Create the diagram for security objects:

```sql
CREATE SCHEMA Security;
GO
```

> If the **Security** schema already exists following a previous trial, do not repeat this command.

3. Create the predicate table function:

```sql
CREATE FUNCTION Security.fn_sales_region
(
    @Region varchar(8000)
)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
(
    SELECT 1 AS access_granted
    WHERE
        (
            USER_NAME() = 'participant@contactemeraudeit.onmicrosoft.com'
            AND @Region = 'Europe'
        )
        OR USER_NAME() = 'dev@contactemeraudeit.onmicrosoft.com'
);
GO
```

4. Associate this function with the **Region** column of the table:

```sql
CREATE SECURITY POLICY Security.SalesFinCorpRegionPolicy
ADD FILTER PREDICATE Security.fn_sales_region(Region)
ON dbo.sales_fincorp
WITH (STATE = ON);
GO
```

5. Check that the policy is active:

```sql
SELECT
    name,
    is_enabled
FROM sys.security_policies
WHERE name = 'SalesFinCorpRegionPolicy';
```

**What you need to see**:

- Policy **SalesFinCorpRegionPolicy** appears with`is_enabled = 1`.

- The function allows all regions for **dev**, only Europe for **participant**, and no lines for other identities.

6. Test the deactivation of the policy without deleting it:

```sql
ALTER SECURITY POLICY Security.SalesFinCorpRegionPolicy
WITH (STATE = OFF);
GO
```

7. Check his new condition:

```sql
SELECT
    name,
    is_enabled
FROM sys.security_policies
WHERE name = 'SalesFinCorpRegionPolicy';
```

**What you need to see**: policy still exists, but`is_enabled = 0`. The RLS filter is no longer applied as long as it remains disabled; other SQL permissions continue to apply.

> **Disable or remove? **`STATE = OFF`maintain the policy and its function so that it can be reused quickly.`DROP SECURITY POLICY`removes the object and is used for final cleaning as presented in Step 6.

8. Reactivate the policy before continuing the SLR tests:

```sql
ALTER SECURITY POLICY Security.SalesFinCorpRegionPolicy
WITH (STATE = ON);
GO
```

9. Relaunch the query on`sys.security_policies`and check that`is_enabled = 1`.

# Layer 4 — Security of columns and objects in SQL termination point (CLS/OLS)

The SLR policy of layer 3 has been abolished. This layer therefore isolates the effect of **column level security (CLS)** in the same **SQL analytics endpoint**:

- the participant can again read all the lines of **dbo.sales fincorp**;
- SQL permissions will allow useful columns and block **Salary**;
- the account **dev** retains full access to rows and columns.

The safety at the object level can be applied with two complementary granularities:

- **Column-Level Security (CLS)** protects one or more specific columns of a table;
- The object-level security (OLS)** applied to the table protects the entire object and prevents any reading of its columns.

The CLS can thus be considered as a targeted form of object security at the column level, while the table OLS acts on the whole table. This layer begins with the CLS and ends with a blockage of the entire table to introduce the next case study.

```sql
SELECT
    principal.name AS PrincipalName,
    permission.state_desc AS PermissionState,
    permission.permission_name AS PermissionName,
    OBJECT_SCHEMA_NAME(permission.major_id) AS SchemaName,
    OBJECT_NAME(permission.major_id) AS ObjectName,
    column_definition.name AS ColumnName
FROM sys.database_permissions AS permission
INNER JOIN sys.database_principals AS principal
    ON permission.grantee_principal_id = principal.principal_id
LEFT JOIN sys.columns AS column_definition
    ON permission.major_id = column_definition.object_id
    AND permission.minor_id = column_definition.column_id
WHERE principal.name = 'participant@contactemeraudeit.onmicrosoft.com'
  AND OBJECT_NAME(permission.major_id) = 'sales_fincorp'
ORDER BY column_definition.column_id;
```

## Step 6 — Extend protection to the whole table with OLS

**Objective**: Switch from a targeted restriction on the column **Salary** to a reading ban on the entire table **dbo.sales fincorp**.

> To clearly isolate the effect of table OLS, the explicit permissions granted or refused at the column level during the CLS test must first be removed.

**Former actions (account dev) — clean CLS**:

1. In Fabric SQL editor or SSMS, reconnect with the account **dev**.

2. Remove authorizations from functional columns:

```sql
REVOKE SELECT
ON OBJECT::dbo.sales_fincorp
(
    TransactionID,
    Region,
    SalesRep,
    Amount,
    ClientName,
    Date
)
FROM [participant@contactemeraudeit.onmicrosoft.com];
GO
```

3. Remove the refusal in column **Salary**:

```sql
REVOKE SELECT
ON OBJECT::dbo.sales_fincorp (Salary)
FROM [participant@contactemeraudeit.onmicrosoft.com];
GO
```

4. With the account **participant**, execute this check request:

```sql
SELECT TOP 10
    Region,
    SalesRep,
    Salary
FROM dbo.sales_fincorp;
```

The request must succeed again. The participant returned to the initial permissions obtained by his role **Workspace Viewer**.

**Former actions (account dev) — apply OLS to table**:

1. Refuse reading the entire table to the participant:

```sql
DENY SELECT
ON OBJECT::dbo.sales_fincorp
TO [participant@contactemeraudeit.onmicrosoft.com];
GO
```

2. Control the recorded permission:

```sql
SELECT
    principal.name AS PrincipalName,
    permission.state_desc AS PermissionState,
    permission.permission_name AS PermissionName,
    OBJECT_SCHEMA_NAME(permission.major_id) AS SchemaName,
    OBJECT_NAME(permission.major_id) AS ObjectName,
    permission.minor_id AS ColumnId
FROM sys.database_permissions AS permission
INNER JOIN sys.database_principals AS principal
    ON permission.grantee_principal_id = principal.principal_id
WHERE principal.name = 'participant@contactemeraudeit.onmicrosoft.com'
  AND OBJECT_NAME(permission.major_id) = 'sales_fincorp';
```

The expected permission is **DENY SELECT** with`ColumnId = 0`, which indicates that the refusal is on the whole table and not on a particular column.

**Actions participant** :

1. Reconnect to the SQL termination point with the account **participant**.

2. Try to read a single non-sensitive column:

```sql
SELECT TOP 10 Region
FROM dbo.sales_fincorp;
```

3. Then try to read the whole table:

```sql
SELECT TOP 10 *
FROM dbo.sales_fincorp;
```

**What you need to see**:

- Both requests fail, including one requesting only **Region**.

- The participant can no longer read any column of **dbo.sales fincorp**.

- The account **dev** can always query the full table.

**Final cleaning by the trainer (dev account)**:

1. Remove the refusal applied to the table:

```sql
REVOKE SELECT
ON OBJECT::dbo.sales_fincorp
FROM [participant@contactemeraudeit.onmicrosoft.com];
GO
```

2. With the account **participant**, reexecute`SELECT TOP 10 Region FROM dbo.sales_fincorp;`and check that the playback is working again.
