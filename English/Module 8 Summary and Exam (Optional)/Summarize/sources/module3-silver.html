Cell 2: Duplication (consumption dedup)

Before executing

The first step of cleaning is eliminate exact duplicates. A duplicate is an identical line on all fields (timestamp, site id, consumption mw, etc.).

Why it's important :
- Doubles = pollution caused by IoT restarts or network replications
- May bias subsequent aggregations (average offset)
- Easy to detect and remove reversible

Approche :
- Use SELECT DISTINCT * : keep one copy of each unique combination
- Write in an intermediate table consumption_dedup (is not the final result)

Attente : change from 18 144 to ~17 280 lines (364 duplicates deleted

Cell 3: Filtering invalid values (consumption clean)

Before executing

After eliminating the duplicates, we filter the valeurs invalides :

  1. NULL en consumption_mw (unusable)
  2. consumption_mw < 0 : sensor error codes or corrupted data
  3. consumption_mw ≥ 10 MW : extreme outlets (max expected capacity ~5 MW/site)

Why these thresholds?
- Data from a real power plant: typical consumption 0.3–3 MW
- Threshold 10 MW = x3 above normal max = fault / sensor
- These outsides bias medium and ML models

Approche :
- Use filter() with logical conditions AND (&)
- F.col() creates a column reference, .isNotNull() / Compares apply logic

Attente : from 17,280 to ~16,380 lines (900 invalid lines, 5 %)

💻 Code

Cell 5: Standardization of date formats (consumption dates fixed)

Before executing

The timestamps in Bronze are heterogeneous (ISO 8601, French dd/MM/yyyy, American). For aggregation and joins, it is necessary only one format: timestamp UTC.

Formats observed :
1. ISO 8601 : 2025-01-02T08:45:00Z or 2025-01-02 08:45:00
2. French: 02/01/2025 08:45:00 (dd/MM/yyyy)
3. American: 01-02-2025 08:45:00 (MM-dd-yyyy)

Approche :
- Use F.coalesce() : try the first format, if NULL Try the second, etc.
- F.to_timestamp(col) : conversion native Spark
- F.to_timestamp(col, pattern) : with custom format

Attente : same number of rows (16,380), but new column timestamp_clean standardized in TIMESTAMP Spark.

Cell 6: Time aggregation (consumption hourly)

Before executing

Gross data are in 15 minutes. For analysis and ML models, we aggregate toheure :
- 4 measurements (00, 15, 30, 45 min) → 1 hourly value
- Calculations: mean (avg), min, max, count (measurements)

Why this aggregation?
1. Dimensional reduction : 18 144 → 4 320 lines (÷4, more handy)
2. Alignement temporel : time = standard for energy markets
3. Noise reduction : 4 point average smoothes sensor microvariations
4. Signs retained : min/max keep the hourly amplitude (deco/peak consumption)

Approche :
- groupBy(date_trunc("hour", timestamp_clean), "site_id") : aggregation by hour and site
- .agg() : aggregation calculations (avg, max, min, count)

Attente : 4,320 lines (6 sites × 30 days × 24 hours = 4,320 exact)

💻 Code

Cell 9: Advanced enrichment (consumption enriched) with baseline, z-score, features ML

Before executing

This is the most complex cell: we create 12 derived columns to support analysis and ML models:

  1. Baseline 7 jours glissants (baseline_7d_mw)
    - Average consumption of the previous 7 days for each site
    - As a "normal" marker

  2. Ratio vs baseline (ratio_vs_baseline)
    - Consommation actuelle ÷ baseline 7j
    - Detect deviations vs normal behaviour (e.g. ratio 1.5 = 50% above baseline)

  3. Z-score (z_score)
    - Average deviation of the site in standard deviation units
    - Formule : (x - µ) / σ

  4. Drapeau anomalies (anomaly)
    - ANOMALY (= very rare, >99.7% probability under normality)
    - "✅ Normal" sinon

  5. Features temporelles (hour_of_day, day_of_week, is_weekend)
    - Detect seasonal patterns (high midnight, peaks evening, different weekend)

  6. Joint reference sites (site_type, capacity_mw, flexible, baseline_mw, curtailment_price_eur_mwh, region)
    - Adds business metadata

  7. Weather joint (temperature_c, wind_speed_ms)
    - Real time in global time (not per site)
    - Explique variation consommation (chaud → AC, vent → moins de chauffage)

  8. Flag maintenance (in_maintenance)
    - Placeholder for future filters

  9. Lags for ML (lag_24h, lag_168h)
    - Consumption J-1 and J-7 (24h and 168h before)
    - Features for recursive models

  10. Colonne prediction (placeholder)

    • Will be filled in cell 10

Cell 10: Prediction model (consumption predictions)

Before executing

We create a simple but effective predictive model by combining three signals via weighted average:

Formule :

prediction = baseline_7d × 0.5 + lag_24h × 0.3 + lag_168h × 0.2

Weight justified :
- 0.5 (baseline 7j) : the most stable signal, represents average trend
- 0.3 (lag 24h) : adjusted for daily deviations (weather, events)
- 0.2 (lag 168h) : capture patterns saisonniers (lundi vs dimanche)

Error prediction :
- prediction_error_mw Real consumption - prediction
- prediction_error_pct : error as a percentage of actual consumption
