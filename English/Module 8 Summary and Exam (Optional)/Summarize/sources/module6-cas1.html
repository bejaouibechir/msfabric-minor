Eventstream – Real Data Processing

Workshop: Real-time wind farm monitoring — Eventstream & KQL Database

You will ingest simulated IoT data (wind turbine sensors) in Microsoft Fabric via Eventstream, store them in a KQL Database, turn them into real time, analyze them with queries KQL, visualize them in a Real-Time Dashboard, accelerate the dashboard with a Materialized View and configure alertes automatiques with Activator.

Expected result: a full-time real-time pipeline that oversees 5 wind turbines, highlights anomalies (overheating, vibration, underperformance), enriches events in the flow and displays a dashboard that can be used in near-real conditions.

⚠️ Educational note on the order of the steps : Workshop starts Python simulator before to configure the destination Eventhouse. This choice is intentional — Fabric needs real data that circulates to validate the JSON scheme in the configuration wizard. If you set the destination without data, the button Finish Stay gray.

Files required

  • wind_turbine_simulator.py — Python script provided in Part 2.3
  • Package Python : azure-eventhub

4.2 — Average turbine output (last 10 minutes) 

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(10m)
| summarize
    AvgPower = avg(PowerOutputKW),
    AvgWind = avg(WindSpeedMs),
    EventCount = count()
  by TurbineId
| order by AvgPower desc

  • where EventTime > ago(10m) Filter the last 10 minutes.

  • summarize ... by TurbineId : Group by turbine and average/occurrence calculation.

  • order by AvgPower desc : The most productive to least productive class.

What you see : Each turbine with its average power, average wind speed and number of recent events.

4.3 — Detection of thermal anomalies (> 95°C) 

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where GeneratorTempC > 95
| project EventTime, TurbineId, GeneratorTempC, PowerOutputKW, WindSpeedMs
| order by GeneratorTempC desc

  • where GeneratorTempC > 95 : Critical threshold beyond the risk of breakage.

  • project : Keeps only the columns useful for diagnosis.

  • order by GeneratorTempC desc The warmest first.

What you see : Only events where the generator exceeded 95°C.

4.5 — Energy efficiency per turbine (5 min window) 

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where WindSpeedMs between (4.0 .. 20.0)
| summarize
    AvgPower = avg(PowerOutputKW),
    AvgWind = avg(WindSpeedMs)
  by TurbineId, bin(EventTime, 5m)
| extend EfficiencyRatio = AvgPower / (AvgWind * AvgWind * AvgWind) * 1000

  • extend EfficiencyRatio = ... / (AvgWind³) * 1000 Simplified efficiency (power / wind3).

  • Useful for comparing efficiency between turbines with equal wind.

What you see : a simplified efficiency ratio per turbine every 5 minutes.

4.8 — Detection of underperformance by comparison of power/vent 

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where WindSpeedMs between (6.0 .. 20.0)
| extend ExpectedPowerKW = min_of(3000.0, pow(WindSpeedMs - 3.5, 2) * 18.0)
| extend PerformanceRatio = iif(ExpectedPowerKW == 0, real(null), PowerOutputKW / ExpectedPowerKW)
| where PerformanceRatio < 0.60
| project EventTime, TurbineId, WindSpeedMs, PowerOutputKW, ExpectedPowerKW, PerformanceRatio
| order by PerformanceRatio asc

  • pow(WindSpeedMs - 3.5, 2) * 18.0 : Expected theoretical power.

  • PerformanceRatio < 0.60 : The turbine produces less than 60% of the expected → underperformance.

What you see : the cases where the power actually produced is far below the expected power.

4.10 — Joint with a small reference table 

let TurbineReference = datatable(TurbineId:string, SiteArea:string, NominalPowerKW:real, CommissionYear:int)
[
    "WT-001", "Nord-Ouest", 3000.0, 2021,
    "WT-002", "Nord-Ouest", 3000.0, 2021,
    "WT-003", "Centre", 3000.0, 2022,
    "WT-004", "Centre", 3000.0, 2022,
    "WT-005", "Sud", 3000.0, 2023
];
TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(15m)
| summarize AvgPower = avg(PowerOutputKW), MaxTemp = max(GeneratorTempC) by TurbineId
| join kind=leftouter TurbineReference on TurbineId
| extend LoadPct = round((AvgPower / NominalPowerKW) * 100.0, 2)
| project TurbineId, SiteArea, CommissionYear, AvgPower, LoadPct, MaxTemp
| order by LoadPct desc

  • let TurbineReference = datatable(...) : Temporary table (site, year, nominal power).

  • join kind=leftouter : Enriches telemetry data with metadata.

  • LoadPct = round(AvgPower / NominalPowerKW * 100, 2) : Charge relative.

What you see : An analysis enriched by reference metadata.

4.11 — Top 3 anomalies per combined score 

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| extend ExpectedPowerKW = min_of(3000.0, pow(WindSpeedMs - 3.5, 2) * 18.0)
| extend UnderPerfPenalty = iif(WindSpeedMs >= 8 and PowerOutputKW < ExpectedPowerKW * 0.6, 25.0, 0.0)
| extend TempPenalty = iif(GeneratorTempC > 95, 50.0, iif(GeneratorTempC > 85, 20.0, 0.0))
| extend VibPenalty = iif(VibrationMmS > 8, 40.0, iif(VibrationMmS > 6, 15.0, 0.0))
| extend AnomalyScore = TempPenalty + VibPenalty + UnderPerfPenalty
| where AnomalyScore > 0
| top 3 by AnomalyScore desc
| project EventTime, TurbineId, GeneratorTempC, VibrationMmS, PowerOutputKW, WindSpeedMs, AnomalyScore

  • Three penalties plus : sous-performance (25), surchauffe (20/50), vibration (15/40).

  • top 3 by AnomalyScore desc : The most serious events first.

What you see : the 3 most worrying events, ranked according to a combined score.

4.12 — Recent production trend compared to two 

let CurrentWindow =
    TurbineEvents
    | extend EventTime = todatetime(Timestamp)
    | where EventTime between (ago(10m) .. now())
    | summarize CurrentAvgPower = avg(PowerOutputKW) by TurbineId;
let PreviousWindow =
    TurbineEvents
    | extend EventTime = todatetime(Timestamp)
    | where EventTime between (ago(20m) .. ago(10m))
    | summarize PreviousAvgPower = avg(PowerOutputKW) by TurbineId;
CurrentWindow
| join kind=inner PreviousWindow on TurbineId
| extend DeltaPower = CurrentAvgPower - PreviousAvgPower
| extend Trend = case(DeltaPower > 150, "HAUSSE", DeltaPower < -150, "BAISSE", "STABLE")
| project TurbineId, PreviousAvgPower, CurrentAvgPower, DeltaPower, Trend
| order by DeltaPower asc

  • windows. Two sub-requests : current window (10m) vs previous window (20m to 10m).

  • join then case(...) : Compares average power → HAUSSE / BAISSE / STABLE.

What you see : if each turbine is up, down or stable from the previous window.

5.7 — Seventh tile: top anomalies

  1. On the Home, cliquer New tile
  2. tab. Paste this query: 
TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| extend ExpectedPowerKW = min_of(3000.0, pow(WindSpeedMs - 3.5, 2) * 18.0)
| extend UnderPerfPenalty = iif(WindSpeedMs >= 8 and PowerOutputKW < ExpectedPowerKW * 0.6, 25.0, 0.0)
| extend TempPenalty = iif(GeneratorTempC > 95, 50.0, iif(GeneratorTempC > 85, 20.0, 0.0))
| extend VibPenalty = iif(VibrationMmS > 8, 40.0, iif(VibrationMmS > 6, 15.0, 0.0))
| extend AnomalyScore = TempPenalty + VibPenalty + UnderPerfPenalty
| where AnomalyScore > 0
| top 10 by AnomalyScore desc
| project EventTime, TurbineId, GeneratorTempC, VibrationMmS, PowerOutputKW, AnomalyScore

  • ExpectedPowerKW = min_of(3000, pow(vitesse - 3.5, 2) * 18) : Max theoretical power according to the wind speed (plated at 3000 kW).

  • Three penalties added : Underperformance (25 pts), overheating (20/50 pts depending on severity), vibration (15/40 pts depending on severity).

  • AnomalyScore = sum of penalties : The higher the score, the more problems the event has.

  • top 10 by AnomalyScore desc : Goes up the 10 most serious events first.

  • Utility : Priority of interventions — first the turbine is treated with the highest score.

Part 6 — Industrial Alert Pipeline : Update Policy + Function + Materialized View

In this part, you will build a complete Alerting System completely in the Eventhouse, without external dependence. The final architecture is:

TurbineEvents → (Update Policy) → fn_DetectAnomaly() → TurbineAlerts → (Materialized View) → MV_AlertSummary → (Dashboard)

💡 Why this approach? The Update Policy is a native mechanism of the Eventhouse: every time ingested in TurbineEvents, the detection function automatically executes and writes anomalies in TurbineAlerts. No email, no Teams, no external dependency. Alerts are immediately requestable and visible in the dashboard.

6.1 — Creating the TurbineAlerts table

  1. Ouvrir WindFarmEventhouse_queryset
  2. Paste and execute this command:
.create table TurbineAlerts (
AlertTime: datetime,
TurbineId: thong,
AlertType: thong,
Severity: thong,
AlertValue: real,
Threshold: real,
Message: thong
)
  1. Cliquer Run

What you need to see : a message of success. The table TurbineAlerts appears in the left panel under Tables.

6.2 — Create fn detectAnomaly detection function

The detection logic of the 3 types of anomalies is centralized in a single reusable function. The Update Policy will call this function — if you want to add a rule, you only change the function.

  1. Paste and execute this command:
.create-or-alter function fn detectAnomaly() {
TurbineEvents
- extend EventTime = todatetime(Timestamp)
• extend ExpectedPowerKW = min of(3000.0, pow(WindSpeedMs - 3.5, 2) * 18.0)
• extend PerformanceRatio = iif(
ExpectedPowerKW == 0 or WindSpeedMs < 6.0 or WindSpeedMs > 20.0,
real(null),
PowerOutputKW / ExpectedPowerKW)
Where GeneratorTempC > 95
or VibrationMmS > 8
or (isnotnull(PerformanceRatio) and PerformanceRatio < 0.60)
External AlertType = box(
GeneratorTempC > 95,
VibrationMmS > 8,
SOUS PERFORMANCE")
Extend AlertValue = box(
GeneratorTempC > 95, GeneratorTempC,
VibrationMmS > 8, VibrationMmS,
round(PerformanceRatio * 100, 1))
Extend Threshold = box(
GeneratorTempC; 95, 95.0,
VibrationMmS > 8, 8.0,
60.0)
Extend Severity = box(
GeneratorTempC > 120 or VibrationMmS > 14,
(Quotation)
Message = strcat(
AlertType, " on ", TurbineId,
" — Value: ", tostring(AlertValue, 2)),
" / Threshold: ", tostring(Threshold)
Project AlertTime = EventTime, TurbineId, AlertType, Severity, AlertValue, Threshold, Message
}
  1. Cliquer Run

What you need to see : a message of success. The function fn_DetectAnomaly appears under Functions in the left panel.

💡 Astuce : Test the function alone before attaching it to the policy — run fn_DetectAnomaly() in the queryet and check that lines of anomalies appear.

6.3 — Activer l'Update Policy

  1. Paste and execute this command:
.alter table TurbineAlerts policy update
@'[{"IsEnabled": true, "Source": "TurbinEvents", "Query": "fn detectAnomaly()", "IsTransactional": false, "PropagateIngestionProperties": false}]'

💡 What's happening now : each batch ingested in TurbineEvents, Fabric automatically executes fn_DetectAnomaly() and writes the anomalies in TurbineAlerts. The pipeline is active in real time.

⚠️ Trap : The Update Policy does not remove data already present in TurbineEvents. It applies only to new ingestions. Wait for a simulator cycle (5 seconds) before checking.

Part 7 — Materialized View on TurbineEvents

💡 Rappel : One MV_AlertSummary on TurbineAlerts has already been established in Part 6.4. This part creates a second Materialized View, mv_turbine_health_1m, on the raw table TurbineEvents. Both views have distinct roles: MV_AlertSummary aggravate alerts, mv_turbine_health_1m aggregates raw telemetry to accelerate the operational dashboard tiles.

In a real context, dashboards often perform the same aggregations permanently. One Materialized View pre-calculate the results once and update them incrementally.

7.1 — Create mv turbine health 1m

  1. In WindFarmEventhouse, cliquer + New → Materialized view
  2. Replace the content with the following command: 
.create-or-alter materialized-view with (backfill=true) mv turbine health 1m on table TurbineEvents
{
TurbineEvents
- extend EventTime = todatetime(Timestamp)
- summarize
AvgPower = avg(PowerOutputKW),
MaxTemp = max(GeneratorTempC),
MaxVibration = max(VibrationMmS),
AvgWind = avg(WindSpeedMs),
EventCount = count()
by TurbineId, bin(EventTime, 1m)
  1. Cliquer Run

What you need to see : a message of success. mv_turbine_health_1m appears under Materialized views.

backfill=true immediately recalculates all historical data. The five aggregates (power, temperature, vibration, wind, count) are pre-calculated per turbine per minute.
