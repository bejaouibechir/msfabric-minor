1.7 - SAMPLE : Combination Roles Workspace × Item Permissions on Lakehouse

This section is one of the most important of the workshop. The Workspace role and the item permissions are not two independent systems: they s'influencent mutuellement, and the observed result is not always intuitive. The tests below were performed in real-life conditions on an active Fabric holding.

⚠️ Attention : the actual behavior may differ from what one would logically expect. This is precisely the educational interest of this chessboard.

Real Observations Matrix (Lakehouse)

Workspace role Permissions granted (Lakehouse + Notebook) Bouton Run Notebook SQL Analytics Endpoint Access Lakehouse Interface Access Overall level observed Educational commentary
Viewer Read + ViewOutput ❌ ✅ Limited SQL Play Only Very restrictive — tables inaccessible without ReadAll
Viewer Read + ViewOutput + ReadAll + Execute / Notebook : Read + Edit + Run ❌ (or very late) ✅ Limited SQL playback OK, Run blocked Even with all the rights item + Notebook, the Viewer role blocks Run
Contributor Read + Write + Reshare + Execute + ReadAll + ViewOutput / Notebook : tous droits ✅ (after latency) ✅ ✅ Good balance The most stable role for demos — to be given priority in training
Member Read + Write + Reshare + Execute + ReadAll + ViewOutput / Notebook : tous droits ❌ ❌ ✅ (plus visible) Inattendu / Instable Loss of Run ET SQL despite higher rights than a Contributor
Admin All rights inherited ✅ ✅ ✅ (create / delete) Total access Comportement normal d'administrateur

The rules to memorize

1 — Workspace is the dominant factor.
Even with ReadAll, Execute, Run and Edit at item level, the role Viewer prevents Run from being executed. The item permissions cannot outclass the limit imposed by the role.

2 — Changing roles can reset granular permissions.
Switch a user from Viewer to Contributor or Member can overwrite already configured item permissions. Revalidate systematically after each change of role.

3 — ReadAll + Execute focus on SQL Analytics Endpoint.
These permissions improve SQL access but do not guarantee the execution of Notebooks. Spark and SQL plans have separate authorisation mechanisms.

4 — The Member behavior. is counter-intuitive.
Member appears to be higher than Contributor, but tests show a loss of Run and SQL Endpoint, while the Lakehouse interface is paradoxically becoming more visible. To be presented as a real feature of Fabric, not as a bug.

5 — Contributor is the role to recommend in training context.
Better balance between Notebook access, SQL access and item management, without administrative rights.

1.7.1 Scenario 1 – Baseline (as clean as possible)

Tested configuration:

  • Role Workspace: Viewer
  • Lakehouse Permissions: Read + ViewOutput uniquement

Result observed:

  • The test account can open the Lakehouse.
  • It can open the SQL analytics endpoint and execute requests.
  • It can see the data via the SQL endpoint (SELECT * FROM ... works).
  • On the other hand, in the Lakehouse interface (Tables / Files), it can neither see nor manipulate data easily.

Conclusion : With minimum permissions (Read + ViewOutput), access via SQL endpoint is already possible, but experience remains limited outside the SQL.

1.7.2 Scenario 2 – Addition of ReadAll

Tested configuration:

  • Role Workspace: Viewer
  • Lakehouse Permissions: Read + ViewOutput + ReadAll + Execute

Result observed:

  • No significant change from Scenario 1.
  • The test account continues to be able to execute queries in the SQL endpoint and view the data.
  • Adding ReadAll did not change the behavior in this regard for SQL endpoint.

Conclusion : In this environment, Read alone is already enough to read data via SQL analytics endpoint. ReadAll does not bring visible benefits in this specific context.

1.7.3 Scenario 3 – Test via Spark (Notebook)

Tested configuration:

  • Role Workspace: Viewer
  • Lakehouse Permissions: Read + ViewOutput + ReadAll + Execute

Result observed:

  • In a Notebook attached to the Lakehouse, the Run button is non visible.
  • The test account cannot run the Notebook, even with ReadAll and Execute granted on the Lakehouse.

Conclusion : ReadAll and Execute on Lakehouse allow access via SQL, but not enough to run a Notebook.

1.7.4 Scenario 4 – Added rights to the Notebook (Viewer)

Tested configuration:

  • Role Workspace: Viewer
  • Lakehouse Permissions: Read + Write + Reshare + Execute + ReadAll + ViewOutput
  • Permissions on the Notebook : Read + Edit + Share + Run

Result observed:

  • Despite all the rights granted on the Notebook, the Run button. remains invisible or does not appear.
  • The test account still cannot run the Notebook.

Conclusion : With the role Viewer, even by giving all possible permissions on the Notebook, execution remains blocked. Workspace is the limiting factor.

1.7.5 Scenario 5 – Switching to Contributor

Tested configuration:

  • Role Workspace: Contributor
  • Lakehouse Permissions: Read + Write + Reshare + Execute + ReadAll + ViewOutput
  • Permissions on the Notebook : Read + Edit + Run

Result observed:

  • The Run button. Notebook becomes visible (sometimes after refreshment or latency).
  • The test account can now run the Notebook cells successfully.
  • SQL endpoint access remains available.

Conclusion : The role Contributor Unlocks execution of Notebooks. This is currently the most stable role for practical demonstrations.

1.7.6 Scenario 6 – Member transition

Tested configuration:

  • Role Workspace: Member
  • Lakehouse Permissions: Read + Write + Reshare + Execute + ReadAll + ViewOutput + SubscribeOneLakeEvents

Result observed:

  • The Run button of the Notebook disappears .
  • The SQL Analytics Endpoint devient inaccessible.
  • The Lakehouse interface (Tables / Files) becomes more visible and accessible.

Conclusion : The Member transition. produces an unexpected and unstable behavior: loss of access to SQL endpoint and execution of Notebook, despite wide permissions.

1.7.7 Scenario 7 – Admin

Tested configuration:

  • Role Workspace: Admin
  • Lakehouse Permissions: Read + Write + Reshare + Execute + ReadAll + ViewOutput + ...

Result observed:

  • The Run button. is visible.
  • The SQL Analytics Endpoint is accessible.
  • Full access to the Lakehouse interface (see, create, delete tables, etc.).

Conclusion : The role Admin gives full access, as expected.

Part 5 - DB roles: Build-in and Custom in Warehouse

Database roles (DB roles) constitute an intermediate security layer between granular SQL permissions (individual GRANT/DENY seen in Part 4) and workspace management. They allow group permissions under a name and assigning users to this group rather than managing rights one by one.

Microsoft Fabric Warehouse exhibits the same fixed roles as SQL Server, accessible in explorer under Security > DB roles (Built-in). It also helps to create Custom roles via CREATE ROLE.
