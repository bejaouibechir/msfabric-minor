## 🎯 Objectif de l'atelier

La couche Bronze d'une Medallion représente le première étape de traitement des données.

Pourquoi cette approche ? La couche Bronze agit comme une **source de vérité immutable**. Elle préserve les données exactement comme elles arrivent des sources

## 📊 Contexte métier

Votre organisation gère un réseau de six sites de production et consommation d'électricité répartis en France.

1. Deux sites industriels (capacités 5 MW et 3,5 MW), 

2. Deux sites commerciaux (2 MW et 1,5 MW) 

3. Deux résidentiels (0,8 MW et 0,6 MW). 

Chaque site est équipé de capteurs IoT transmettant toutes les 15 minutes la consommation d'électricité pendant 30 jours. 

Des données complémentaires arrivent de plusieurs sources : 

1. Prix spot du marché EPEX, 

2. Conditions météorologiques, 

3. Données de référence des sites et événements de maintenance.

**Le problème :** 

Ces données brutes arrivent en formats variés (timestamps incohérents, valeurs numériques manquantes ou invalides représentées par des codes erreur comme -888 ou -999), avec des doublons et une qualité inégale selon la source. Avant d'exploiter ces données pour de l'analyse ou du machine learning, il faut d'abord les centraliser, en préserver l'intégrité, et documenter les anomalies. C'est exactement le rôle de la couche Bronze.

## 📝 Cellule 1 : Configuration Spark et création du schéma Bronze

## 📝 Cellule 2 : Import consumption_raw.csv → Table Delta

### 🔍 Avant d'exécuter

Vous charger le premier fichier source, `consumption_raw.csv`, qui contient les données de consommation d'électricité capturées toutes les 15 minutes.

 PySpark offre une API `spark.read.format("csv")` idéale pour charger des CSV. 

Les options `header=true` et `inferSchema=true` instruisent Spark à traiter la première ligne comme entête et à déduire automatiquement les types de colonnes (timestamp, integer, string, etc.). 

Après lecture en DataFrame, vous écrivez les données au format Delta (format optimisé pour le data lakehouse) dans le schéma `bronze`. 

Le mode `overwrite` écrase toute table existante de même nom, garantissant un reset complet à chaque exécution.

Le comptage des lignes (`count()`) est une étape critique :

 En data engineering, on vérifie systématiquement que le nombre de lignes chargées correspond à l'attente. Une divergence majeure indiquerait un problème de lecture ou de troncature.

### 💻 Code

```python
# Charger le CSV avec PySpark
df_consumption = spark.read.format("csv") \
    .option("header", "true") \
    .option("inferSchema", "true") \
    .load("Files/data_bronze_notebooks/consumption_raw.csv")

# Compter les lignes avant écriture
nb_lignes = df_consumption.count()

# Créer la table dans le schéma bronze
df_consumption.write.mode("overwrite").format("delta").saveAsTable("bronze.consumption_raw")

print(f"✅ Table bronze.consumption_raw créée : {nb_lignes} lignes")
```

### 📤 Résultat

```
✅ Table bronze.consumption_raw créée : 18144 lignes
```

### 💡 Interprétation

- **18 144 lignes** chargées, soit 17 280 théoriques (6 sites × 4 mesures/h × 24 h × 30 j) + 864 doublons
- **Table Delta** `bronze.consumption_raw` : persistante et interrogeable en SQL
- **Source de vérité** : données stockées telles quelles, sans transformation

## 📝 Cellule 4 : Diagnostic qualité de consumption_raw

### 🔍 Avant d'exécuter

Vous effectuez à présent un diagnostic statistique de la table `consumption_raw`. Cette requête SQL agrégée compte plusieurs dimensions de qualité : le nombre total de lignes, le nombre de combinaisons uniques (timestamp, site_id) pour détecter les doublons, les valeurs NULL (absence totale), les valeurs négatives (codes erreur), et les outliers (consommation > 10 MW, anormalement haute). Ces métriques forment la base line qualité pour la couche Bronze et serviront de benchmark pour évaluer l'impact du nettoyage en Silver.

### 💻 Code

```sql
%%sql
-- Compter les NULL, codes erreur, doublons
SELECT
    COUNT(*) as total_rows,
    COUNT(DISTINCT timestamp, site_id) as unique_rows,
    COUNT(*) - COUNT(DISTINCT timestamp, site_id) as duplicates,
    SUM(CASE WHEN consumption_mw IS NULL THEN 1 ELSE 0 END) as null_values,
    SUM(CASE WHEN consumption_mw < 0 THEN 1 ELSE 0 END) as error_codes,
    SUM(CASE WHEN consumption_mw > 10 THEN 1 ELSE 0 END) as outliers
FROM bronze.consumption_raw
```

### 📤 Résultat

| total_rows | unique_rows | duplicates | null_values | error_codes | outliers |
| ---------- | ----------- | ---------- | ----------- | ----------- | -------- |
| 18144      | 17280       | 864        | 554         | 319         | 27       |

### 💡 Interprétation

- **864 doublons** (4,8 %) : retransmissions réseau ou recalibrage capteur, à dédupliquer en Silver
- **554 NULL** (3 %) : défaillance capteur ou maintenance, à filtrer ou imputer
- **319 codes erreur** (1,8 %) : `-888` défaut capteur, `-999` panne réseau, `-777` calibrage
- **27 outliers** (0,15 %) : consommation > 10 MW alors que la capacité maximale est de 5 MW, à investiguer
- **Baseline qualité** : ces chiffres serviront de référence pour mesurer l'effet du nettoyage Silver
