# Atelier 2 — Industrialiser un job Spark incrémental

## Objectifs de l’atelier

Dans cet atelier, vous transformez une ingestion de fichiers de capteurs en un traitement incrémental, contrôlé et pilotable par code avec une **Spark Job Definition** Microsoft Fabric.

À la fin de l’atelier, vous saurez :

- produire des lots JSON Lines reproductibles ;
- utiliser **Structured Streaming** avec un schéma explicite ;
- traiter uniquement les nouveaux fichiers avec `availableNow` et un checkpoint ;
- normaliser des horodatages hétérogènes ;
- appliquer des règles de qualité et isoler les rejets ;
- rendre un `foreachBatch` idempotent avec **MERGE Delta** ;
- écrire un journal d’audit par micro-lot ;
- configurer une stratégie de nouvelle tentative ;
- lancer et suivre une Spark Job Definition depuis Python sans secret.

**Durée indicative :** 3 h à 4 h  
**Niveau :** avancé  
**Langages :** Python et PySpark

---

## État des lieux

Vous disposez du workspace `WS_Energie_Renouvelable` et du Lakehouse `LH_Energie_Bronze`.

L’Atelier 1 a introduit `argparse`, `logging`, une fonction `main()`, des modules réutilisables et les MERGE Delta. L’Atelier 2 reprend ces principes sans dépendre des tables créées précédemment.

Un simulateur local produit des mesures provenant de capteurs d’une usine solaire-éolienne :

| Colonne | Description |
|---|---|
| `capteur_id` | Identifiant du capteur |
| `site_id` | Site de production |
| `timestamp` | Instant de la mesure |
| `grandeur` | Température, irradiance, vent ou puissance |
| `valeur` | Valeur numérique observée |
| `unite` | Unité attendue pour la grandeur |
| `qualite` | Indication fournie par la source |

Les lots contiennent volontairement des valeurs nulles, des valeurs hors plage, des doublons et deux formats de timestamp.

---

## Problématique

Un traitement complet relit inutilement tous les fichiers, consomme davantage de capacité et peut introduire des doublons. Un traitement continu maintenu actif serait disproportionné pour quelques dépôts périodiques.

Vous devez donc construire un job borné : à chaque lancement, il traite tout ce qui est disponible, mémorise sa progression, puis s’arrête et libère les ressources Spark.

Le traitement doit résister aux reprises. Une relance sans nouveau fichier doit lire zéro nouvelle ligne. Une reprise après panne ne doit pas dupliquer les données déjà écrites.

---

- ✅ utiliser l’identité Azure CLI ou `DefaultAzureCredential`, jamais un secret ;

## Solution proposée

La solution contient trois scripts :

| Fichier | Rôle |
|---|---|
| `traitement_capteurs.py` | Lecture incrémentale, qualité, MERGE et audit |
| `capteurs_sjd_utils.py` | Normalisation et validation pures, schéma Spark |
| `lancer_sjd.py` | Lancement REST et suivi jusqu’à l’état terminal |

Elle utilise trois nouvelles tables :

| Table | Contenu |
|---|---|
| `mesures_capteurs_sjd` | Mesures valides et typées |
| `mesures_quarantaine_sjd` | Lignes rejetées et motif |
| `journal_runs_sjd` | Audit des micro-lots et des exécutions vides |

La clé métier de la table Silver est `capteur_id + timestamp + grandeur`. Elle suppose qu’un capteur ne publie qu’une valeur d’une même grandeur au même instant. Dans un système réel, un identifiant de mesure immuable ou un numéro de séquence est préférable.

## Étape 4 — Normaliser les timestamps

Le générateur produit deux formats :

```text
2025-02-01T00:00:00Z
01/02/2025 00:00:00
```

Le module pur essaie successivement les deux formats et renvoie un `datetime` UTC. Dans Spark, utilisez `coalesce` :

```python
timestamp_normalise = F.coalesce(
    F.to_timestamp("timestamp", "yyyy-MM-dd'T'HH:mm:ssX"),
    F.to_timestamp("timestamp", "dd/MM/yyyy HH:mm:ss"),
)
```

Une date hétérogène correctement reconnue n’est pas rejetée. Une chaîne ne correspondant à aucun format reçoit le motif `TIMESTAMP_INVALIDE`.

✅ Le contrôle local a normalisé les 55 timestamps hétérogènes attendus.

## Étape 6 — Configurer le checkpoint durable

Utilisez un emplacement distinct pour cette requête :

```text
Files/checkpoints/sjd2_capteurs
```

Le checkpoint conserve les fichiers déjà traités, les offsets, les métadonnées et l’état du stream. Ne le partagez jamais avec une autre requête.

⚠️ La suppression ou la corruption du checkpoint rompt le contrat de reprise. Avec un nouveau checkpoint, la source fichier peut être relue depuis le début. Les MERGE limitent alors les doublons dans les tables, mais le coût de recalcul demeure.

Le chemin relatif est résolu dans le Lakehouse par défaut de la Spark Job Definition. La présence réelle du dossier après le premier run reste `[à constater]`.

## Étape 7 — Utiliser `foreachBatch` et `availableNow`

💻 **Code**

```python
requete = (
    flux.writeStream
        .queryName("sjd2-capteurs-available-now")
        .foreachBatch(traiter_batch)
        .option("checkpointLocation", args.checkpoint_path)
        .trigger(availableNow=True)
        .start()
)
requete.awaitTermination()
```

`availableNow` traite toutes les données disponibles au lancement, valide le checkpoint, puis arrête la requête. `awaitTermination()` est indispensable : sans lui, la Spark Job Definition pourrait atteindre un état terminal alors que le stream fonctionne encore de manière asynchrone.

Ce mode est différent d’un stream continu : il évite de conserver une session Spark active entre deux arrivées de fichiers.

✅ La documentation Fabric confirme l’usage de `availableNow` pour un job incrémental planifié et l’exécution de Structured Streaming dans une Spark Job Definition.

## Étape 8 — Rendre les écritures idempotentes

Dans chaque micro-lot, classez les doublons avec une fenêtre sur la clé métier. Séparez ensuite les lignes valides et invalides.

Pour `mesures_capteurs_sjd`, appliquez :

```python
(DeltaTable.forName(spark, TABLE_MESURES).alias("cible")
 .merge(source.alias("source"), condition_cle)
 .whenMatchedUpdateAll()
 .whenNotMatchedInsertAll()
 .execute())
```

Pour la quarantaine, calculez un `rejet_id` déterministe à partir du fichier, des valeurs métier et du rang du doublon, puis appliquez un second MERGE.

`foreachBatch` offre une sémantique au moins une fois : Spark peut rejouer un micro-lot. Les sinks personnalisés doivent donc être idempotents.

## Points d’attention

### Coût, capacité F2 et checkpoint

Chaque lancement chauffe une session Spark. `availableNow` libère le calcul après le backlog, mais plusieurs jobs peuvent être mis en file d’attente. La consommation reste `[à constater]`. Un checkpoint appartient à une seule requête : ne le copiez ni ne le supprimez sans analyser la compatibilité et préparer le rejeu.

### Ordre d’arrivée

La source fichier découvre les nouveaux fichiers, mais leur ordre ne doit pas porter une règle métier implicite. La clé et les timestamps doivent suffire à rendre le résultat déterministe.

### Idempotence

Le checkpoint réduit les relectures ; il ne remplace pas l’idempotence du sink. Un `foreachBatch` peut être rejoué. Les MERGE sur les clés déterministes protègent les tables.

### Authentification

Utilisez l’identité de l’utilisateur en local et une identité gérée ou un principal de service contrôlé pour une automatisation hébergée. N’insérez jamais un jeton dans les arguments ou les variables d’un pipeline.
