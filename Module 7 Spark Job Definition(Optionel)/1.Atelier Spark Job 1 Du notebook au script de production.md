# Atelier 1 — Du notebook au script de production avec une Spark Job Definition

## Objectifs de l’atelier

Dans cet atelier, vous transformez une ingestion explorée dans un notebook en un script Python exploitable comme **Spark Job Definition** dans Microsoft Fabric.

Vous travaillez sur les données d’une usine d’énergie renouvelable : besoins énergétiques, production solaire et production éolienne.

À la fin de l’atelier, vous saurez :

- structurer un traitement PySpark sous forme de script Python ;
- isoler les schémas et transformations réutilisables dans un module ;
- lire les données depuis une API REST ou depuis **OneLake** ;
- créer et paramétrer une **Spark Job Definition** ;
- rendre le chargement idempotent grâce à un **MERGE Delta** ;
- diagnostiquer une exécution dans les écrans de supervision Fabric ;
- appeler le traitement depuis un pipeline de données.

**Durée indicative :** 3 h à 4 h  
**Niveau :** avancé  
**Langage :** Python et PySpark

---

## État des lieux

Le workspace `WS_Energie_Renouvelable` contient le Lakehouse `LH_Energie_Bronze`.

Les ateliers précédents ont introduit trois familles de données :

| Jeu de données | Colonnes métier                                                                                      |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| Besoins        | `Timestamp`, `Zone`, `Consommation_kWh`, `Type_Energie`, `Cout_Euro`                                 |
| Solaire        | `PanneauID`, `Date`, `Zone_Installation`, `Production_kWh`, `Ensoleillement_Heures`, `Rendement_Pct` |
| Éolien         | `TurbineID`, `Timestamp`, `Vitesse_Vent_ms`, `Production_kWh`, `Statut`                              |

Une Azure Function peut exposer ces données par API. Elle peut toutefois être arrêtée pour limiter les coûts. Le traitement doit donc proposer deux sources équivalentes :

- `api` pour appeler les trois endpoints HTTP ;
- `files` pour lire les fichiers JSON déposés dans `Files/landing_sjd/`.

---

## Problématique

Un notebook est idéal pour explorer, visualiser et mettre au point un traitement. En production, une ingestion récurrente doit également être paramétrable, versionnable, testable et observable sans dépendre de cellules exécutées manuellement.

Vous devez convertir le prototype en un programme Python autonome tout en conservant la capacité de le tester dans un notebook.

Le programme ne doit jamais ajouter de doublons lors d’une nouvelle exécution. Une première exécution de 30 lignes, suivie d’une seconde exécution avec les mêmes données, doit laisser la table à 30 lignes.

---

## Ce qui doit être fait

Votre solution doit respecter les contraintes suivantes :

- ✅ utiliser `argparse`, `logging`, une fonction `main()` et des annotations de type ;
- ✅ accepter `--source`, `--base-url`, `--dataset` et `--landing-path` ;
- ✅ produire le même DataFrame typé en mode `api` et en mode `files` ;
- ✅ ajouter `ingested_at` et `source` ;
- ✅ charger les tables avec un **MERGE Delta** ;
- ✅ ne jamais modifier les tables Bronze existantes ;
- ✅ écrire uniquement dans les tables suffixées `_sjd` ;
- ✅ conserver l’URL de l’API hors du code source ;
- ✅ séparer les schémas et fonctions réutilisables dans `energie_sjd_utils.py` ;
- ✅ prévoir un diagnostic contrôlé en cas d’échec.

## Solution proposée

La solution comprend deux fichiers Python :

| Fichier                | Rôle                                                      |
| ---------------------- | --------------------------------------------------------- |
| `ingestion_energie.py` | Point d’entrée, lecture, transformation et MERGE          |
| `energie_sjd_utils.py` | Métadonnées des jeux, schémas, conversions et clés métier |

Les fichiers nécessaires à l’atelier sont disponibles dans ce module :

| Élément                     | Emplacement                                        |
| --------------------------- | -------------------------------------------------- |

Les trois tables cibles sont :

| Dataset   | Table cible                | Clé métier du MERGE       |
| --------- | -------------------------- | ------------------------- |

Ces clés composites sont adaptées au jeu d’exercice, qui ne fournit aucun identifiant technique. Elles supposent qu’une zone, un panneau ou une turbine ne produit qu’une mesure au même instant. Dans un système réel, privilégiez un identifiant immuable fourni par la source.

Ajoutez ensuite les colonnes techniques :

## Étape 5 — Lire depuis l’API ou depuis les fichiers

Ouvrez `scripts atelier 1/ingestion_energie.py` et repérez l’analyse des arguments :

```python
parser.add_argument("--source", choices=("api", "files"), required=True)
parser.add_argument("--base-url")
parser.add_argument("--dataset", choices=tuple(DATASETS), required=True)
parser.add_argument("--landing-path", default="Files/landing_sjd")
```

En mode `api`, le script construit l’URL à partir de `--base-url` et de l’endpoint associé au dataset. Il utilise un délai d’attente HTTP et vérifie la réponse avant de créer le DataFrame.

En mode `files`, il lit un tableau JSON racine :

```python
df = (
    spark.read
         .option("multiline", "true")
         .schema(schema_for(dataset))
         .json(f"{landing_path.rstrip('/')}/{spec.file_name}")
)
```

## Étape 6 — Implémenter le MERGE Delta

Avant le MERGE, refusez les clés nulles et éliminez les doublons du lot avec `dropDuplicates(business_keys)`. Construisez ensuite la condition de rapprochement :

```python
merge_condition = " AND ".join(
    f"target.`{key}` <=> source.`{key}`" for key in business_keys
)
```

Si la table n’existe pas, créez-la avec `write.format("delta").saveAsTable(...)`. Sinon, appelez `DeltaTable.forName(...)`, puis enchaînez `merge`, `whenMatchedUpdateAll`, `whenNotMatchedInsertAll` et `execute`.

Le `MERGE` met à jour une mesure connue et insère une nouvelle mesure. Il ne transforme donc pas une relance à l’identique en doublon.

## Points d’attention

### Capacité F2

Chaque démarrage Spark mobilise la capacité. Exécutez les datasets séquentiellement, évitez les relances inutiles et arrêtez les tests lorsque les résultats sont collectés. La consommation réelle de cet atelier est `[à constater]`.

### Service Azure arrêté

Le mode `files` est le chemin de secours officiel de cet atelier. Ne redémarrez pas l’Azure Function sans accord. Le mode `api` ne doit pas bloquer la validation du script.

### Clés composites

Les clés choisies ne remplacent pas un identifiant source. Une correction arrivée avec la même clé remplace les valeurs existantes. Deux mesures légitimes partageant la même clé seraient fusionnées : documentez toujours cette limite.

### Paramètres dynamiques du pipeline

La capacité de remplacement est documentée, mais le champ d’interface et l’expression exacte restent `[à constater]`. Conservez les variantes proposées tant que le comportement n’a pas été validé sur le tenant.

### Bibliothèque `requests`
