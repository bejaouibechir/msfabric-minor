# Couche 1 — RBAC Workspace

## Étape 1 — Attribuer le rôle Workspace Viewer au compte participant

**Objectif** : Créer un environnement Fabric minimal, attribuer le rôle **Viewer** au compte participant et vérifier concrètement les accès accordés par ce rôle sur un Lakehouse et son point de terminaison SQL.

**Pourquoi** :  
Le rôle Workspace Viewer est le seul rôle qui n’autorise aucune modification ni exécution dangereuse.

Il constitue le plafond de sécurité pour tous les utilisateurs finaux.

| Rôle            | Capacités principales                                                               | Gestion des accès et du partage                                                                          | Usage type                                       |
| --------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Admin**       | Dispose du contrôle complet sur le workspace et son contenu.                        | Peut ajouter ou retirer tous les utilisateurs                                                            | Propriétaire ou administrateur de la plateforme. |
| **Member**      | Peut créer, modifier, exécuter et supprimer les objets et les données du workspace. | Peut ajouter des **Members**, des **Contributors** et des **Viewers** outre que les droit de contributor | Responsable d’équipe ou gestionnaire de contenu  |
| **Contributor** | Peut, comme un **Member**, créer, modifier, exécuter et supprimer les objets        | Ne peut pas gérer les rôles du workspace ni ajouter des utilisateurs.                                    | Développeur ou concepteur                        |
| **Viewer**      | Peut consulter le contenu du workspace sans le modifier. .                          | Ne peut pas gérer les accès.                                                                             | Lecteur, analyste métier                         |

> 

**Actions formateur (compte dev – Workspace Admin)** :

1. Connectez-vous à Microsoft Fabric avec le compte **dev**.

2. Créez un workspace nommé **FinCorp_Initial** et vérifiez que le compte **dev** possède le rôle **Admin** sur ce workspace.

3. Dans le workspace **FinCorp_Initial**, sélectionnez **+ New item**, puis créez un **Lakehouse** nommé **LH_FinCorp**.

4. Ouvrez **LH_FinCorp**, puis chargez le fichier `Data/Sales_FinCorp.csv` fourni avec l’atelier dans la section **Files** du Lakehouse :
   
   - sélectionnez **Files** puis **Upload** ;
   - choisissez **Upload files** ;
   - sélectionnez le fichier `Sales_FinCorp.csv` ;
   - vérifiez que le fichier apparaît sous **Files**.

5. Revenez dans le workspace **FinCorp_Initial** et créez un notebook nommé **NB_Load_SalesFinCorp**.

6. Attachez **LH_FinCorp** comme Lakehouse par défaut du notebook.

7. Conservez une seule cellule PySpark dans le notebook, puis saisissez et exécutez le code suivant :

```python

df.write.mode("overwrite").format("delta").saveAsTable("sales_fincorp")
display(spark.table("sales_fincorp"))
```

8. Revenez dans **LH_FinCorp**, actualisez la section **Tables** et vérifiez que la table **sales_fincorp** est visible.

9. Ouvrez le workspace **FinCorp_Initial**, puis cliquez sur **Manage access** en haut à droite.

10. Cliquez sur **+ Add people or groups**.

11. Dans la zone de recherche, saisissez le nom ou l’adresse du compte **participant**, puis sélectionnez-le.

12. Dans la liste des rôles, choisissez **Viewer**.

13. Cliquez sur **Add**.

**Ce que le formateur doit vérifier** :

- Le workspace **FinCorp_Initial** contient le Lakehouse **LH_FinCorp**, son point de terminaison SQL et le notebook **NB_Load_SalesFinCorp**.

- Le fichier `Sales_FinCorp.csv` apparaît dans **Files** et la table **sales_fincorp** apparaît dans **Tables**.

- Dans le **SQL analytics endpoint** associé au Lakehouse, le participant peut visualiser les tables, consulter les données et exécuter des requêtes SQL en lecture, notamment sur **dbo.sales_fincorp**.

- Dans le notebook **NB_Load_SalesFinCorp**, le participant peut visualiser les cellules ainsi que les résultats des exécutions précédentes, mais il ne peut pas exécuter les cellules ni lancer une nouvelle session.

# Couche 3 — Sécurité des lignes dans le point de terminaison SQL (RLS)

Cette couche réutilise le Lakehouse **LH_FinCorp** et sa table Delta **sales_fincorp**. La RLS n’est plus définie dans le modèle sémantique : elle est appliquée dans le **SQL analytics endpoint** au moyen d’une fonction table de prédicat et d’une **SECURITY POLICY**.

La fonction reçoit la valeur **Region** de chaque ligne, contrôle l’identité retournée par `USER_NAME()`, puis autorise ou refuse la ligne. Le modèle sémantique doit donc interroger le point de terminaison SQL avec le SSO de l’utilisateur. Un modèle **Direct Lake on OneLake** ne convient pas à ce scénario, car il contourne le moteur SQL et sa politique.

---

## Étape 1 — Préparer la table et le point de terminaison SQL

**Objectif** : Vérifier que la table **dbo.sales_fincorp** est disponible et que les identités SQL des deux comptes sont correctement reconnues.

## Étape 2 — Créer la fonction de prédicat et la politique RLS

**Objectif** : Autoriser le compte **participant** à lire uniquement les lignes Europe tout en conservant l’accès complet du compte **dev**.

**Pourquoi** :
La fonction table est évaluée par le moteur SQL pour chaque ligne. Elle retourne une ligne contenant la valeur `1` lorsque l’accès est autorisé et un jeu vide lorsqu’il doit être refusé. La **SECURITY POLICY** applique cette fonction automatiquement à chaque requête sur **dbo.sales_fincorp**.

**Actions formateur (compte dev)** :

1. Ouvrez une nouvelle requête dans le **SQL analytics endpoint** de **LH_FinCorp**.

2. Créez le schéma destiné aux objets de sécurité :

```sql
CREATE SCHEMA Security;
GO
```

> Si le schéma **Security** existe déjà à la suite d’un essai précédent, ne réexécutez pas cette commande.

3. Créez la fonction table de prédicat :

```sql
CREATE FUNCTION Security.fn_sales_region
(
    @Region varchar(8000)
)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
(
    SELECT 1 AS access_granted
    WHERE
        (
            USER_NAME() = 'participant@contactemeraudeit.onmicrosoft.com'
            AND @Region = 'Europe'
        )
        OR USER_NAME() = 'dev@contactemeraudeit.onmicrosoft.com'
);
GO
```

4. Associez cette fonction à la colonne **Region** de la table :

```sql
CREATE SECURITY POLICY Security.SalesFinCorpRegionPolicy
ADD FILTER PREDICATE Security.fn_sales_region(Region)
ON dbo.sales_fincorp
WITH (STATE = ON);
GO
```

5. Vérifiez que la politique est active :

```sql
SELECT
    name,
    is_enabled
FROM sys.security_policies
WHERE name = 'SalesFinCorpRegionPolicy';
```

**Ce que vous devez voir** :

- La politique **SalesFinCorpRegionPolicy** apparaît avec `is_enabled = 1`.

- La fonction autorise toutes les régions pour **dev**, uniquement Europe pour **participant**, et aucune ligne pour les autres identités.

# Couche 4 — Sécurité des colonnes dans le point de terminaison SQL (CLS)

La sécurité de la colonne sensible **Salary** est appliquée dans le même **SQL analytics endpoint** que la RLS de la couche 3. Cette sécurité est une **Column-Level Security (CLS)** SQL : elle accorde au participant la lecture des colonnes nécessaires au rapport et lui refuse explicitement la lecture de **Salary**.

La RLS et la CLS sont donc cumulées par le moteur SQL :

- la fonction et la **SECURITY POLICY** limitent les lignes du participant à la région Europe ;
- les permissions SQL limitent les colonnes accessibles et bloquent **Salary** ;
- le compte **dev** conserve l’accès complet aux lignes et aux colonnes.

---

## Étape 2 — Appliquer la CLS au compte participant

**Objectif** : Autoriser uniquement les colonnes nécessaires au rapport et refuser explicitement la colonne **Salary** au participant.

```sql
SELECT
    principal.name AS PrincipalName,
    permission.state_desc AS PermissionState,
    permission.permission_name AS PermissionName,
    OBJECT_SCHEMA_NAME(permission.major_id) AS SchemaName,
    OBJECT_NAME(permission.major_id) AS ObjectName,
    column_definition.name AS ColumnName
FROM sys.database_permissions AS permission
INNER JOIN sys.database_principals AS principal
    ON permission.grantee_principal_id = principal.principal_id
LEFT JOIN sys.columns AS column_definition
    ON permission.major_id = column_definition.object_id
    AND permission.minor_id = column_definition.column_id
WHERE principal.name = 'participant@contactemeraudeit.onmicrosoft.com'
  AND OBJECT_NAME(permission.major_id) = 'sales_fincorp'
ORDER BY column_definition.column_id;
```
